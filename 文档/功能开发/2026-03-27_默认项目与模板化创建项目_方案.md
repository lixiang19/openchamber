# 默认项目与模板化创建项目 方案

- 状态：草案
- 日期：2026-03-27
- Owner：Codex / ridge
- 目标版本/里程碑：项目管理首期重构

## 1. 背景与问题

- 背景：用户希望软件打开后就自动拥有一个可用项目，不再先经历“空项目态 + 选目录”的冷启动流程，同时侧边栏除了“添加已有项目”之外，还要支持“创建新项目”。
- 现象/痛点：当前后端已经偷偷做了一个 `starter project` 引导，`packages/web/server/index.js:2367` 仍会在无项目时创建旧产品路径下的 starter 目录，但这套逻辑是隐藏的、命名也不对外，前端没有“默认项目”的明确产品语义。
- 现象/痛点：当前前端只有“添加已有项目”链路，入口来自 `packages/ui/src/components/session/sidebar/SidebarHeader.tsx:65`、`packages/ui/src/components/session/SessionSidebar.tsx:673`、`packages/ui/src/components/session/DirectoryExplorerDialog.tsx:84`，本质是选一个现成目录并注册到项目列表，不是“从模板创建新项目”。
- 现象/痛点：虽然服务端已经有 `/api/projects/create-from-template`，并且 `packages/web/server/lib/projects/template.js:100` 已经能写模板文件，但它仍然是“单一 starter 模板 + 临时接口”的半成品，前端没有接入，默认项目与手动创建项目也不是同一模型。
- 现象/痛点：`packages/ui/src/components/session/SessionDialogs.tsx:125` 仍保留“当项目数为 0 时弹目录选择”的启动兜底，这会和“自动生成默认项目”产品目标冲突。
- 成功定义：应用在“启动时无项目”场景下自动生成并激活默认项目；侧边栏/设置页/移动端都新增“创建项目”入口；默认项目与手动创建项目走同一套模板注册与项目创建模型；“添加项目”继续只处理外部已有目录。

## 2. 目标与非目标

- 目标：
  - 把当前隐藏的 `starter project` 重构成正式的“默认项目”产品能力。
  - 引入统一的“受管项目（managed project）”模型，默认项目与手动创建项目共用同一套模板注册、路径规划、写盘与 settings 持久化流程。
  - 固定受管项目根目录为 `~/ridge/projects`，默认项目和新建项目都创建在这个目录下。
  - 在主侧边栏、项目设置页、移动端项目页统一提供“创建项目”和“添加项目”两个入口。
  - 首期提供模板选择能力，并让默认项目自动使用默认模板初始化。
- 非目标：
  - 不支持用户自定义项目父目录；首期“创建项目”必须创建在固定受管目录下。
  - 不做用户自定义模板市场、远程模板仓库、模板安装中心。
  - 不把“添加已有项目”改造成模板创建；外部目录导入仍然保持独立语义。
  - 不保留 `starter project` 作为长期特殊分支；本轮要统一模型，而不是在旧逻辑外面再包一层 UI。
  - 不在本轮把项目创建和“自动创建首个会话”强绑定；创建完成后只激活项目，不自动发起对话。

## 3. 现状探索（Explorer）

- 入口与调用链：
  - `packages/ui/src/components/session/sidebar/SidebarHeader.tsx:65` - 当前侧边栏项目入口只有一个 folder-add 按钮，语义是“添加项目”。
  - `packages/ui/src/components/session/SessionSidebar.tsx:673` - 点击后要么走桌面目录选择，要么通过 `sessionEvents` 打开目录对话框。
  - `packages/ui/src/components/session/DirectoryExplorerDialog.tsx:84` - 对话框确认后调用 `addProject(...)`，仅把已有目录注册成项目。
  - `packages/ui/src/stores/useProjectsStore.ts:360` - `addProject()` 负责路径归一化、按路径去重、写入项目列表、切换 active project。
  - `packages/ui/src/stores/useProjectsStore.ts:430` - `setActiveProject()` 会同步 `runtimeClient` 与目录 store，因此“创建项目完成后激活项目”应当复用这一层，不要在组件里散落状态更新。
  - `packages/ui/src/components/session/SessionDialogs.tsx:125` - 当 `projects.length === 0` 时，前端还会主动弹目录选择，这和默认项目自动创建目标冲突。
- 关键数据结构/状态：
  - `packages/ui/src/lib/api/types.ts:492` - 当前 `ProjectEntry` 只有 `id/path/label/icon/color/addedAt/lastOpenedAt/sidebarCollapsed`，无法表达“这是默认项目、模板创建项目还是导入项目”。
  - `packages/ui/src/lib/desktop.ts:25` - `DesktopSettings` 里以 `projects` 与 `activeProjectId` 持久化项目列表。
  - `packages/web/server/index.js:2348` - 当前已有 starter bootstrap state，但它是围绕旧的 `starter project` 命名搭出来的特殊状态，不适合作为长期抽象。
- 约束与坑点：
  - 现在后端已经存在 `ensureStarterProjectBootstrapped()` 和 `create-from-template`，但两者都围绕“starter”命名；如果继续往上补 UI，只会固化错误抽象。
  - 项目列表在桌面、Web、本地存储、settings API 之间都有同步链路，任何“创建项目”都必须以 settings 为单一事实源，不能只改 local store。
  - UI 上同样的项目入口分布在主侧边栏、设置页、移动端多个位置，如果不抽统一 action，很容易一个入口支持创建、另一个入口继续只有添加。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `packages/web/server/index.js:7621` 的 `/api/config/settings` 已经在读取配置时调用 `ensureStarterProjectBootstrapped()`，说明“启动时自动补首个项目”最合适的挂载点就在服务端 settings bootstrap，而不是前端页面初始化。
  - `packages/web/server/lib/projects/template.js:100` 已经有“模板写盘”原语，因此不需要把模板文件生成逻辑塞进 UI；正确方向是把它升级成模板注册中心。
  - `packages/ui/src/stores/useProjectsStore.ts:286` 已经把项目列表变化统一写回 `updateDesktopSettings(...)`，因此“项目创建成功后写 settings 并同步 active project”应由 store/服务端统一完成，而不是组件自己拼本地状态。
  - `packages/ui/src/components/sections/projects/ProjectsSidebar.tsx:26`、`packages/ui/src/components/mobile/MobileChatShell.tsx:256` 已经存在多个“添加项目”入口，说明本轮必须抽项目入口动作，不然创建能力会碎成多个版本。
  - Pi 相关迁移文档强调项目要走 Pi 原生宿主，而不是继续补 OpenCode 兼容外壳；这个功能与 Pi 本身耦合不深，最重要的是不要再引入额外兼容层，把项目管理域在当前宿主内收口即可。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：删除“隐藏 starter 特例”思路，把它重构成正式的“受管项目”体系：服务端维护固定受管根目录 `~/ridge/projects` 和模板注册表；启动时无项目则自动生成“默认项目”；UI 新增“创建项目”入口，用户输入项目名并选择模板，即可在该目录下创建并注册新项目。
- 取舍：首版不支持用户任意指定新项目位置，换来受管项目路径规则统一、默认项目与手动创建真正共用一条链路、服务端能够稳定推导默认项目与模板元数据。
- 影响面：会改服务端项目 bootstrap 与模板模块、项目创建 API、`ProjectEntry` 结构、主侧边栏/设置页/移动端项目入口，以及无项目启动时的目录弹窗逻辑。

核心设计如下：

```text
受管项目根目录
~/ridge/projects/
  default-project/          # 默认项目，显示名“默认项目”
  my-demo/                  # 用户创建项目
  landing-page/             # 用户创建项目
```

统一抽象如下：

```ts
interface ManagedProjectTemplate {
  id: string;
  label: string;
  description: string;
  internalOnly?: boolean;
  create(targetDirectory: string, projectName: string): Promise<CreateTemplateResult>;
}

interface ProjectEntry {
  id: string;
  path: string;
  label?: string;
  source?: 'default' | 'managed' | 'external';
  templateId?: string | null;
  icon?: string | null;
  color?: string | null;
  addedAt?: number;
  lastOpenedAt?: number;
}
```

受管项目创建入口统一为：

```ts
createManagedProject({
  name,
  templateId,
  source, // 'default' | 'managed'
}): Promise<{
  project: ProjectEntry;
  settings: DesktopSettings;
  targetDirectory: string;
}>
```

### 5.2 风险与回滚

- 风险：
  - 旧的 `starter` 命名散落在服务端：缓解措施是本轮直接统一重命名为 `default project / managed project`，不再保留双概念并存。
  - `ProjectEntry` 扩字段后，前端某些只按旧结构读写的逻辑可能遗漏：缓解措施是所有 settings 清洗函数、项目 store、移动端/设置页选择器统一更新。
  - 同一项目名在固定根目录下冲突：缓解措施是严格报错“项目目录已存在且非空”，不自动改名，不做隐式兜底。
  - 启动时如果服务端和前端都还保留“无项目兜底”，会出现重复弹窗或双重初始化：缓解措施是以前端删除无项目目录选择分支、服务端单点 bootstrap 为准。
- 回滚：
  - 回滚不是继续保留 `starter` 与 `managed` 两套长期并存，而是把本次“受管项目体系”所在提交整体回退。
  - 在实施期间，如果服务端 API 已改而前端未接上，必须一并回退同批提交，避免出现“默认项目自动创建了，但 UI 无法创建项目”的半完成状态。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：
  1. 用户启动应用。
  2. 服务端读取 settings；若当前项目列表为空，则创建 `~/ridge/projects/default-project`，按默认模板写盘，并把它写入 `projects` 与 `activeProjectId`。
  3. 前端收到 settings 后直接进入有项目态，不再弹“请选择目录”。
  4. 用户在侧边栏点击“创建项目”。
  5. 弹出创建项目对话框：输入项目名、选择模板。
  6. 提交后，服务端在 `~/ridge/projects/<项目名目录>` 下创建项目，写入模板文件，注册到 settings，并设为 active project。
  7. 前端同步 settings，项目列表立刻出现新项目并切换为当前项目。
- 交互入口：
  - 主侧边栏：保留“添加项目”，新增并列“创建项目”。
  - 项目设置页：在 `ProjectsSidebar` 头部把单一 add 按钮扩成“创建 / 添加”双入口。
  - 移动端项目页：头部按钮区同样提供“创建 / 添加”双入口。
- 边界条件：
  - 项目名为空、清洗后为空、超长、包含非法路径字符：禁止提交并给出明确错误。
  - 目标目录已存在且非空：直接失败，不自动加后缀，不做“项目 (1)” 兜底。
  - 模板不存在或被移除：服务端返回 400，前端提示并保持表单状态。
  - 用户手动删除默认项目目录：只要 settings 中仍有项目记录，按普通“目录丢失项目”处理；若启动时 settings 里已经无项目，则重新生成默认项目。

### 6.2 接口与契约

- API/函数签名：
  - `GET /api/projects/templates`：`void -> { templates: ManagedProjectTemplateSummary[] }`
  - `POST /api/projects/create-managed`：`{ name: string; templateId: string } -> { success: true; project: ProjectEntry; settings: DesktopSettings; targetDirectory: string }`
  - `ensureDefaultProjectInitialized(settings): Promise<DesktopSettings>`：服务端内部函数，在 settings 读取阶段执行。
  - `createManagedProject(input): Promise<CreateManagedProjectResult>`：服务端内部统一创建入口，默认项目与手动创建都走这里。
- 错误码/异常：
  - `400`：项目名非法、模板不存在、请求参数缺失。
  - `409`：目标项目目录已存在且非空。
  - `500`：模板写盘失败、settings 持久化失败。
  - 前端不吞错，直接展示服务端错误文案。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `DesktopSettings.projects[].source`：`'default' | 'managed' | 'external'`（标记项目来源，供 UI 和 bootstrap 判断）。
  - `DesktopSettings.projects[].templateId`：`string | null`（记录项目使用的模板）。
  - `DesktopSettings.defaultProjectBootstrap`：`{ completed: boolean; updatedAt: number; projectId?: string; projectPath?: string }`。
- 路径规则：
  - 受管项目根目录固定为 `~/ridge/projects`。
  - 默认项目目录固定为 `~/ridge/projects/default-project`，显示名固定为“默认项目”。
  - 手动创建项目目录为 `~/ridge/projects/<sanitized-project-name>`。
- 模板布局：
  - 模板注册逻辑放到 `packages/web/server/lib/projects/templates/`。
  - 每个模板都是一个独立文件夹，目录内可包含任意文件与子目录。
  - 每个模板根目录必须带 `template.json`，用于声明 `id`、`label`、`description` 与需要做变量渲染的文件列表。
  - 首期至少提供两个内置模板：`blank-node` 与 `blank-web`；默认项目自动使用 `blank-node`。
- 迁移策略：
  - 不保留旧的 `starter project` 特例接口与命名。
  - 现有 `projects` 条目在下一次 settings 清洗时补齐 `source`：受管目录下的默认项目记为 `default`，受管目录下的其他模板项目记为 `managed`，其他现存项目记为 `external`。
  - 旧的 starter bootstrap key 不再继续扩展，统一切换到新的 `defaultProjectBootstrap`。

### 6.4 兼容性与发布

- 兼容策略：不维护“旧 starter 特例 + 新 managed project”双模型；同一版本内直接替换到统一受管项目体系。
- 发布步骤：
  1. 先重构服务端项目模板与 bootstrap 模块，确保 settings 读取即返回新的默认项目语义。
  2. 再接入 `GET /api/projects/templates` 与 `POST /api/projects/create-managed`。
  3. 最后替换前端三个入口（主侧边栏 / 设置页 / 移动端）并移除无项目目录弹窗分支。

### 6.5 可观测性

- 日志：
  - 记录默认项目是否创建、目标路径、模板 ID、settings 写入结果。
  - 记录手动创建项目的 name/templateId/targetDirectory/result。
  - 记录模板创建失败与路径冲突原因。
- 指标：
  - `default_project_created_total`
  - `managed_project_created_total`
  - `managed_project_create_failed_total`
- 告警：
  - 同一启动过程中多次触发默认项目初始化视为异常。
  - 模板创建失败率持续升高时需要排查模板文件生成逻辑。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] 全新 settings 场景下首次打开应用，项目列表中直接出现“默认项目”，且不再弹目录选择。
  - [ ] 默认项目目录实际生成在 `~/ridge/projects/default-project`，模板文件完整写入。
  - [ ] 侧边栏、设置页、移动端项目页都能看到“创建项目”与“添加项目”两个入口。
  - [ ] 用户输入项目名并选择模板后，项目会在固定受管目录下创建成功、自动加入项目列表并切成 active project。
  - [ ] “添加项目”仍然只导入已有目录，不会误走模板创建流程。
  - [ ] 目标目录已存在且非空时，创建项目明确失败，不出现自动重命名或隐式覆盖。
- 非功能验收：
  - [ ] 性能：默认项目初始化仅发生在“项目列表为空”的启动路径，且不明显拉长首页首屏时间。
  - [ ] 可靠性：默认项目 bootstrap 与手动创建共享同一后端创建函数，不存在两套写盘逻辑。
  - [ ] 安全：项目创建仅允许写入固定受管根目录，不接受任意相对路径或越权父目录输入。
