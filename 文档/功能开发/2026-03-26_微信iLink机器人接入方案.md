# 微信iLink机器人接入方案

- 状态：已确认
- 日期：2026-03-26
- Owner：openchamber
- 目标版本/里程碑：下一轮 Pi 接入迭代

## 1. 背景与问题

- 背景：`corespeed-io/wechatbot` 已经提供了可直接复用的 Node.js SDK `@wechatbot/wechatbot`，并且仓库里还给出了现成的 `@wechatbot/pi-agent` 桥接扩展示例；这说明“微信作为外部消息通道接入 Pi”已经有清晰的官方实现思路。
- 现象/痛点：当前 openchamber 只有 Pi 原生会话链路，没有微信入口；如果不新增独立接入层，微信消息就无法进入现有会话、也无法把 Pi 的回复稳定回传到微信。
- 成功定义：扫码登录后，微信消息可以进入 openchamber 的 Pi 会话，Pi 回复可以回到同一微信对话，同时保持现有主 UI 和 Pi 会话主链路不被破坏。

## 2. 目标与非目标

- 目标：
  - 把 `@wechatbot/wechatbot` 接进 openchamber 的服务端运行时，作为微信消息入口。
  - 将微信会话映射到 Pi 会话，做到“微信消息 -> Pi prompt -> 微信回复”的闭环。
  - 支持扫码登录、重连、typing 状态、基础文本回复，后续再补媒体能力。
  - 让 UI 负责展示连接状态、二维码和会话绑定信息，而不是让 SDK 自己承担展示职责。
- 非目标：
  - 不把微信接入做成 OpenCode 兼容层，也不把它翻译成旧协议。
  - 不在这次方案里做多平台消息聚合，不接 Telegram/Discord/企业微信。
  - 不把微信能力塞进前端消息 reducer 当“伪消息”；消息源必须先进入服务端会话层。

## 3. 现状探索（Explorer）

- 入口与调用链：
  - `packages/web/server/lib/pi/sdk-host.js:140` - `createPiSdkHost()` 是 Pi 会话总控，负责 `createSession`、`prompt`、`abort`、交互请求响应和事件订阅。
  - `packages/web/server/index.js:5999` - `:6120` - `/api/pi/sessions`、`/api/pi/sessions/:sessionId/prompt`、`/api/pi/events` 等路由把 Pi 会话能力暴露给前端。
  - `packages/ui/src/lib/pi/client.ts:16` - `:89` - 前端通过 REST + SSE 读写 Pi 状态，不直接连后端 session 对象。
  - `packages/ui/src/hooks/useEventStream.ts:133` - `:174` - 前端先拉会话快照，再订阅 SSE 事件，把事件投影进本地状态。
  - `packages/ui/src/lib/pi/reducer.ts:579` - `:632` - 前端只接受固定的 Pi ServerEvent 形态。
- 关键数据结构/状态：
  - `packages/ui/src/lib/pi/types.ts:129` - `PiServerEvent` 是当前前端事件边界。
  - `packages/ui/src/lib/openchamberConfig.ts:3` - `:18` - 用户级配置已经统一落在 `~/.config/openchamber`，适合继续承接桥接配置。
  - `packages/web/server/lib/github/auth.js:11` - 现有服务端也会把认证状态写入 `~/.config/openchamber/settings.json`，说明“集成级状态持久化”是已有模式。
- 约束与坑点：
  - 当前主链路是“服务端权威、前端投影”，微信接入必须先进入服务端，不适合只改 UI。
  - 传输层是 REST + SSE，不是 websocket，也不是任意事件总线。
  - 会话和目录绑定是既有规则；微信侧必须显式决定绑定到哪个 Pi 会话或哪个工作目录。
  - 现有 Pi 宿主已经是 SDK 宿主，不是插件兼容层；新增微信入口应作为并列能力接入，不要继续做协议翻译。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `@wechatbot/wechatbot` 是 Node.js 侧的核心 SDK，支持 `login()`、`start()`、`onMessage()`、`reply()`、`sendTyping()`、媒体收发和可插拔存储，且要求 Node.js >= 22。
  - 仓库里的 `pi-agent` 扩展已经证明了最直接的桥接形态：`/wechat` 触发扫码登录，微信消息被转成 Pi prompt，Pi 完成后再回写到微信。
  - 官方协议文档明确了 QR 登录、35 秒长轮询、`context_token`、`errcode: -14` 失效重登、以及媒体 CDN 加密链路，这意味着微信侧必须作为独立传输层处理，不能靠前端补丁式接入。
  - SDK 本身不会渲染二维码，调用方必须接管 `onQrUrl`，所以 openchamber 需要自己决定二维码展示位置与状态呈现方式。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：在 `packages/web/server` 内新增一个微信 Gateway 服务，使用 `@wechatbot/wechatbot` 负责扫码、长轮询、typing、媒体和持久化，并把微信入口收敛到聊天区域的会话级按钮，让当前会话直接成为微信消息的绑定目标。
- 取舍：
  - 选“服务端网关”而不是“Pi CLI 扩展包”，因为 openchamber 本身已经是 Pi 宿主，不是 Pi CLI；把微信能力放在现有服务端里，能直接复用 `createPiSdkHost()`、现有配置体系和 UI。
  - 选“微信会话 -> Pi 会话”绑定，而不是把微信消息直接塞进前端 store，因为当前架构已经明确是服务端权威，前端只做投影。
- 影响面：
  - 服务端会新增微信连接、登录、消息转发和会话绑定逻辑。
  - UI 会在聊天区域新增会话级微信按钮与弹窗，用来显示 QR、连接状态、重连/断开操作，并把当前会话声明为微信目标。
  - Pi 会话主链路不改，只是多了一个外部输入通道。

### 5.2 风险与回滚

- 风险：
  - 微信登录状态和凭证需要稳定持久化，否则重启后会反复扫码。
  - 微信入站消息和 Pi 回复存在异步链路，若会话绑定不清晰，容易把消息回错会话。
  - 媒体下载和回传可能带来较大内存占用，尤其是文件/视频。
  - 运行环境如果低于 Node 22，SDK 无法直接工作。
- 回滚：
  - 微信 Gateway 作为独立启动模块接入，回滚时直接停止它的 bootstrap，不再加载微信桥接配置即可；Pi 主链路继续保持不变。
  - 如果后续验证发现桥接模型不合适，可以整模块移除，不需要改 Pi 宿主协议。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 入口设计：
  - 主入口是聊天区域右上角的会话级微信按钮，按钮触发一个会话级弹窗。
  - 弹窗里的主按钮会先把“当前会话”声明为微信目标，再执行 `连接微信` / `重新扫码` / `断开`。
  - 不再提供设置页里的全局桥接入口，因为微信接入的真实语义是“消息绑定到当前会话”，不是全局偏好。
- 用户流程：
  1. 用户在某个聊天会话里点击右上角 `WeChat` 按钮。
  2. 前端先把当前会话设为微信目标，再调用后端 `start`，后端创建 `WeChatBot` 实例并请求登录。
  3. 后端返回 `qrUrl`，前端把它渲染成二维码，并显示“等待扫码 / 已扫码 / 已连接”。
  4. 微信消息进入后，网关优先把消息绑定到当前声明的 Pi 会话，调用 `prompt()` 发送文本或媒体描述。
  5. Pi 生成回复后，由网关调用 `reply()` 回传到同一微信对话。
  6. 断开时前端调用 `stop`，后端停止长轮询并清理本次连接状态。
- 界面状态：
  - `idle`：显示 `连接微信` 按钮。
  - `starting`：显示二维码和“等待扫码”。
  - `scanned`：显示“已扫码，等待确认”。
  - `connected`：显示微信账号、最近一次连接时间、`重新扫码` 和 `断开` 按钮。
  - `error`：显示错误文本和重试按钮。
- 边界条件：
  - QR 过期后必须走重新登录，不做“静默兜底”。
  - `session:expired` 或 `errcode: -14` 必须明确进入重连流程。
  - 如果当前微信会话还没有绑定 Pi 会话，先创建会话或要求用户显式选择会话，不能随便猜默认值。
  - 若回复包含 Markdown，发送前要转成微信可读的纯文本。

### 6.2 接口与契约

- API/函数签名：
  - `WechatBridgeService.start(options) -> Promise<{ accountId: string | null; qrUrl: string | null }>`：启动微信登录和轮询。
  - `WechatBridgeService.stop() -> Promise<void>`：停止长轮询并释放资源。
  - `WechatBridgeService.getStatus() -> { connected: boolean; accountId: string | null; lastError: string | null }`：返回当前连接状态。
  - `WechatBridgeService.handleIncomingMessage(msg) -> Promise<void>`：把微信消息映射到 Pi 会话。
  - `PiSessionRouter.bindWechatUser(userId, sessionId) -> void`：维护微信用户与 Pi 会话的绑定关系。
- 建议 HTTP 形态：
  - `POST /api/wechat-bridge/start`：开始登录，返回 `qrUrl` 和当前状态。
  - `POST /api/wechat-bridge/stop`：断开连接并清理当前轮询。
  - `GET /api/wechat-bridge/status`：返回是否已连接、微信账号、最近错误。
  - `POST /api/wechat-bridge/bind`：把当前微信用户绑定到某个 Pi 会话。
  - `POST /api/wechat-bridge/default-target`：把当前聊天会话声明为微信目标。
- 错误码/异常：
  - 登录失败、扫码过期、会话失效、媒体下载失败都要作为显式错误上报到 UI 和日志，不允许吞掉。
  - 对 `session:expired` 的处理必须是重连或断开，不做模糊降级。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `wechatBridge.enabled`：`boolean`（是否启动桥接）。
  - `wechatBridge.accountId`：`string | null`（当前微信账号）。
  - `wechatBridge.defaultSessionId`：`string | null`（当前聊天区域声明的微信目标会话）。
  - `wechatBridge.bindings`：`Array<{ userId: string; sessionId: string; cwd: string | null; updatedAt: number }>`（微信用户到 Pi 会话的映射）。
  - `wechatBridge.lastQrUrl`：`string | null`（最后一次登录二维码地址，仅短期状态）。
- 迁移策略：
  - 新增桥接配置走独立 JSON 文件或 `settings.json` 的新顶层字段都可以，但必须一次性定型，不做兼容分叉。
  - 推荐持久化路径与现有模式一致，放在 `~/.config/openchamber/` 下；微信 SDK 自己的登录状态继续交给 `~/.wechatbot/`。

### 6.4 兼容性与发布

- 兼容策略：
  - 不做 OpenCode 兼容，也不做协议翻译层。
  - 微信桥接默认只在用户显式启用后启动，避免未配置时抢占账号或拖慢主程序启动。
- 发布步骤：
  1. 先落服务端网关和持久化。
  2. 再接聊天区域的会话级 QR/状态弹窗。
  3. 最后补媒体与错误处理。

### 6.5 可观测性

- 日志：
  - 登录发起、二维码生成、扫码成功、登录确认、消息入站、Pi prompt 发起、回复成功、回复失败、重连、断开。
- 指标：
  - 当前连接状态、重连次数、二维码刷新次数、消息往返耗时、媒体处理失败次数。
- 告警：
  - 短时间内连续扫码过期或反复登录失败。
  - 入站消息积压但无回复。
  - 媒体下载/上传连续失败。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] 扫码后可以成功登录微信，并在 UI 或日志中看到已连接状态。
  - [ ] 微信发送一条文本消息，openchamber 能把它转成 Pi 会话输入并收到回复。
  - [ ] Pi 回复能回到同一微信对话，且不会串到其他会话。
  - [ ] 重启后凭证能恢复，不需要每次重新扫码。
- 非功能验收：
  - [ ] 性能：微信网关启动不阻塞 openchamber 主 UI 启动。
  - [ ] 可靠性：`session:expired` 能触发明确重连，不出现静默卡死。
  - [ ] 安全：登录凭证与桥接配置只落在用户配置目录，不写入仓库。

## 8. 里程碑与任务（Milestones）

> 原则：只拆 1-3 个里程碑；每个里程碑都必须有可验证的交付物与退出标准。里程碑内再列任务，但不要过度细碎。

### M1：微信网关骨架与登录状态

- 交付物：后端可以创建 `WeChatBot` 实例、完成扫码登录、持久化登录状态，并把连接状态暴露给 UI。
- 退出标准：扫描二维码后能稳定连上微信，刷新页面或重启服务后能恢复状态。
- 任务：
  - [ ] 增加 `@wechatbot/wechatbot` 依赖与服务端网关模块（文件/模块：`packages/web/server/lib/wechatbot/*`）验收：能启动并拿到 QR URL。
  - [ ] 把登录状态和错误状态接到现有服务端启动/停止流程（文件/模块：`packages/web/server/index.js`）验收：服务重启时不会残留脏连接。
  - [ ] 增加桥接配置读写位置（文件/模块：`packages/ui/src/lib/openchamberConfig.ts` 或服务端同类配置）验收：启用/禁用状态可持久化。

### M2：微信消息 -> Pi 会话 -> 微信回复

- 交付物：微信文本消息可以稳定进入 Pi 会话，Pi 回复可以按原会话回到微信。
- 退出标准：同一个微信用户发三轮对话，Pi 上下文能连续保持，不串号、不丢消息。
- 任务：
  - [ ] 设计微信用户与 Pi 会话的绑定表（文件/模块：`packages/web/server/lib/wechatbot/*`）验收：同一用户始终落到同一会话。
  - [ ] 接入 typing 状态与回复发送（文件/模块：微信网关服务）验收：用户在微信里能看到“正在输入中”。
  - [ ] 复用现有 Pi 会话宿主 `createPiSdkHost()` 的 prompt 路径（文件/模块：`packages/web/server/lib/pi/sdk-host.js`）验收：微信输入会进入既有 Pi 会话生命周期。

### M3：媒体、会话级弹窗与收尾

- 交付物：支持基础媒体回传，聊天区域有会话级连接弹窗和断开/重连操作，日志和错误状态可见。
- 退出标准：图片/文件至少能走通一种媒体路径，连接异常有明确提示，用户能在当前会话里手动断开并重新连接。
- 任务：
  - [ ] 增加图片/文件/视频的下载与转发策略（文件/模块：微信网关服务）验收：媒体不再只显示文本占位。
  - [ ] 在聊天区域增加会话级桥接状态与二维码弹窗（文件/模块：`packages/ui/src/components/chat/*`）验收：用户能在当前会话里直接完成接入。
  - [ ] 补日志、错误和重连统计（文件/模块：服务端网关）验收：可定位登录失败、会话失效和媒体处理失败。

## 9. 执行计划与闭环

- 执行顺序：M1 -> M2 -> M3
- 每个里程碑验证：
  - M1：只做服务启动 + 扫码登录 + 状态查看，不跑全量构建；用 `bun run --cwd packages/web type-check` 做最小静态验证。
  - M2：手工发一条微信文本，确认 openchamber 收到、Pi 有回复、微信收到回信。
  - M3：手工发图片或文件，确认媒体链路和 UI 面板可用。
- 最终回报：
  - 输出按文件/模块划分的变更摘要。
  - 按验收标准逐项勾选完成情况。
  - 说明残留风险与回滚点是否仍然可用。
  - 如果还有后续改造，明确下一步只沿着哪个里程碑继续。
