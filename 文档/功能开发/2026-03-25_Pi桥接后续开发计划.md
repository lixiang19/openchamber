# Pi 原生重构与 OpenCode 彻底移除计划

- 状态：待实施
- 日期：2026-03-25
- 关联提交：`3fa088d0b4f86483cae4587bb8e23f8f667fef96`
- 本文结论优先级：最高
- 适用范围：后续所有聊天、会话、工具、交互、设置相关开发

## 1. 最终决策

从现在开始，项目采用以下硬性方向：

- `opencode` 不再作为运行时选项保留。
- `opencode` 相关启动、代理、健康检查、配置、onboarding、类型依赖，最终全部移除。
- 当前 `pi --mode rpc` 方案不再作为正式路线继续开发。
- Pi 集成必须改为 SDK 内嵌方式。
- 前端必须以 Pi 为基础彻底改造。
- 不要兼容层。
- 不要翻译层。
- 不要再把 Pi 映射成 OpenCode 风格协议、事件、消息结构。
- 不要再做“中立协议层”来同时兼容 OpenCode 和 Pi。

一句话：项目要变成“Pi 原生应用”，不是“兼容 Pi 的 OpenCode 外壳”。

## 2. 对当前提交的定位

提交 `3fa088d0b4f86483cae4587bb8e23f8f667fef96` 只能视为一次试错性原型。

它证明了两件事：

- 现有 UI 某些组件形式上可以承接 Pi 的部分数据。
- 以 bridge/兼容方式接 Pi，会把项目继续锁死在 OpenCode 体系里。

因此，这次提交不应作为后续正式架构的基础，只能作为“哪些 UI 交互值得保留参考”的素材来源。

### 2.1 可参考的内容

- `QuestionCard` 在 `input/select/confirm` 这类交互上的界面形态。
- `AssistantTextPart` 展示 custom message 的经验。
- `ToolPart` 展示 subagent/task 风格输出的经验。
- 若干测试里体现出的附件、提问、工具结果边界情况。

### 2.2 不应继续演进的内容

- `packages/web/server/lib/pi/runtime.js` 现有 RPC 运行时主线。
- `packages/web/server/lib/pi/bridge-schema.js` 现有 envelope/bridge 设计。
- `packages/web/server/index.js` 里的 OpenCode/Pi 双 runtime 并存方案。
- 所有“把 Pi 重新包装成 OpenCode 协议”的代码。
- 前端继续依赖 `opencodeClient` 作为核心 API 抽象。
- 所有“先做一层兼容，再慢慢替换”的架构性借口。

## 3. 明确禁止的技术方向

下面这些方向后续一律不要再做。

### 3.1 禁止 OpenCode 兼容层

不要再做：

- Pi -> OpenCode API 的兼容转换
- Pi -> OpenCode SSE 事件名转换
- Pi -> OpenCode `Message/Part` 结构映射
- Pi -> OpenCode question/permission 结构映射
- 前端继续消费 OpenCode 风格 store，再把 Pi 塞进去

原因：

- 这不是迁移，只是继续用 OpenCode 当系统内核。
- 每新增一个 Pi 能力，都会被兼容层重新扭曲一次。
- 复杂度会长期叠加，不会自然消失。

### 3.2 禁止“中立翻译层”

不要把“兼容层”换个名字继续存在，比如：

- 通用 conversation adapter
- runtime-agnostic event layer
- vendor-neutral message protocol
- event mapper 兼容 Pi/OpenCode 双方

这类设计在当前阶段本质上仍然是在保留双体系。

你已经明确不要兼容层，因此后续前端和服务端都应直接以 Pi 的概念工作。

### 3.3 禁止 RPC sidecar 作为正式架构

不要再把下面这些当主线能力继续补：

- `pi --mode rpc`
- 子进程 stdin/stdout 命令通道
- request/response timeout queue
- envelope parser
- 再把 envelope 翻译给前端

RPC 最多只能作为一次原型探索的历史残留，不能再进入正式架构。

## 4. 新架构原则

## 4.1 服务端：Pi SDK 原生宿主

服务端应该直接做这件事：

- 使用 `createAgentSession()` / `AgentSession` 创建会话。
- 直接持有 Pi session 实例。
- 直接订阅 Pi session 原生事件。
- 直接处理 Pi 的 tool execution、message、extension UI request。
- 直接把 Pi 需要的请求/响应生命周期落到服务端状态里。

服务端不应该做这件事：

- 不把 Pi 包装成 OpenCode 后端。
- 不把 Pi 事件改名成 OpenCode 事件。
- 不把 Pi 请求伪造成 OpenCode question/permission。
- 不维护一个“Pi 兼容 API 层”给旧前端继续用。

## 4.2 前端：Pi 原生模型重构

前端应该直接做这件事：

- 直接围绕 Pi 的 session、event、message、tool execution、extension UI request 来设计 store 和组件。
- 聊天输入框、消息列表、工具卡片、交互卡片都按 Pi 的实际语义重写。
- settings 和控制面板只暴露 Pi 真正存在且真实生效的能力。

前端不应该做这件事：

- 不再把 Pi 数据先翻成 OpenCode `Message/Part` 再渲染。
- 不再先翻成所谓“统一消息格式”再渲染。
- 不再继续围绕 OpenCode 的 providers/agents/models/session store 修修补补。

## 4.3 允许的“变形”仅限传输序列化

唯一允许保留的“转换”，只能是网络传输所必需的序列化：

- 把服务端内存里的 Pi 数据序列化成 JSON 传给浏览器。
- 把浏览器的用户输入序列化成服务端请求。

这不属于兼容层。

但下面这些都属于不允许的语义翻译：

- 改事件名
- 改消息角色语义
- 把 tool execution 重新包装成旧格式 part
- 把 extension UI request 改造成旧式 question/permission 数据结构

## 5. 必须删除的历史包袱

## 5.1 服务端必须删除的东西

重点范围：

- `packages/web/server/index.js` 里所有 OpenCode 生命周期代码
- `packages/web/server/lib/opencode/*`
- `packages/web/server/lib/pi/runtime.js` 当前 RPC 运行时
- `packages/web/server/lib/pi/bridge-schema.js` 当前 bridge 设计
- 所有只为兼容 OpenCode 而存在的 API 和 SSE 路由

目标：

- 不再启动 `opencode`
- 不再探测 OpenCode port
- 不再存在 OpenCode proxy
- 不再存在 OpenCode 风格健康检查
- 不再存在 Pi -> OpenCode 的桥接路由

## 5.2 前端必须删除的东西

重点范围：

- `packages/ui/src/lib/opencode/client.ts` 的中心地位
- `packages/ui/src/lib/openCodeStatus.ts`
- OpenCode CLI onboarding
- 基于 OpenCode config/providers/agents 的聊天前置依赖
- 基于 OpenCode `Message/Part` 的主消息链路
- 基于 OpenCode 事件名的业务逻辑

目标：

- 不再要求 OpenCode CLI
- 不再使用 OpenCode readiness 作为系统可用性判断
- 不再依赖 OpenCode provider/model/agent 配置才能发消息
- 不再让前端主链路理解 OpenCode 协议

## 6. 前端重构的具体要求

这是这次决策里最重要的部分。

## 6.1 前端不是“适配 Pi”，而是“改成 Pi”

后续前端开发目标应改为：

- 会话列表按 Pi session 管理方式设计
- 消息列表按 Pi message/event 设计
- 工具执行展示按 Pi tool execution 生命周期设计
- 交互卡片按 Pi extension UI request 设计
- 输入框提交按 Pi prompt/session API 设计

也就是说，前端的概念体系要直接换掉，而不是再做一层映射。

## 6.2 组件可以复用，数据模型不能继续复用旧抽象

可以复用：

- `QuestionCard` 的视觉布局思路
- `ToolPart` 的视觉容器和展开折叠交互
- `AssistantTextPart` 的 custom block 视觉表达

不能继续复用：

- OpenCode `Part` 作为组件输入主类型
- OpenCode `Session/Message` 作为 store 真源
- “先写入旧 store，再让 UI 继续工作”的过渡策略

原则：UI 可以借壳，数据模型必须换血。

## 6.3 前端 store 必须直接面向 Pi

后续应新增或重构的 store 应直接表达：

- Pi session 列表
- Pi session 当前状态
- Pi message stream
- Pi tool execution 状态
- Pi extension UI request 队列
- Pi 侧当前可见的能力/配置

不要再定义一套为了兼容旧逻辑而存在的中间层 store。

## 6.4 设置页和输入区必须按 Pi 真实能力收敛

要求：

- 如果 Pi SDK 当前没有稳定暴露 provider/model 切换，就不要强制保留这些选择器。
- 如果 Agent 选择在 Pi 当前接法里并不真实生效，就不要继续显示成主控制项。
- 用户只应看到真实可控、真实生效的设置项。

## 7. 新的实施顺序

## M1：先拆前端对 OpenCode 的核心依赖（P0）

目标：停止前端继续围绕 OpenCode 数据模型开发。

### 任务 1：识别并冻结所有聊天主链路中的 OpenCode 核心依赖

重点排查：

- `packages/ui/src/lib/opencode/client.ts`
- `packages/ui/src/stores/useConfigStore.ts`
- `packages/ui/src/hooks/useEventStream.ts`
- `packages/ui/src/components/chat/*`
- `packages/ui/src/stores/useSessionStore.ts`

输出要求：

- 列出哪些地方直接依赖 OpenCode API
- 列出哪些地方直接依赖 OpenCode 类型
- 列出哪些地方直接依赖 OpenCode 事件名
- 标明哪些必须重写，哪些只可复用 UI 外壳

验收：

- 有一份清晰的前端拆除清单，后续任务不再含糊说“慢慢替换”。

### 任务 2：停止继续扩展旧的 `opencodeClient`

要求：

- 不再给 `packages/ui/src/lib/opencode/client.ts` 增加任何面向 Pi 的新逻辑。
- 它只作为历史残留过渡存在，等待删除。

验收：

- 新代码不再往 `opencodeClient` 上挂 Pi 功能。

## M2：建立 Pi 原生前端数据流（P0）

目标：前端主链路直接消费 Pi 语义，而不是任何兼容格式。

### 任务 3：定义 Pi 原生前端状态模型

这里不是做“中立模型”，而是直接做 Pi 模型的前端表达。

建议最小范围：

- `PiSessionViewState`
- `PiMessageViewState`
- `PiToolExecutionViewState`
- `PiInteractiveRequestViewState`

要求：

- 字段命名、生命周期、状态变化直接贴合 Pi SDK 事件和请求。
- 不为了兼容旧组件去故意模仿 OpenCode 类型。

验收：

- 新状态模型不再出现 OpenCode `Part` 那套核心概念。

### 任务 4：重写前端事件摄取链路

要求：

- 前端直接处理 Pi session event 流。
- store 更新逻辑直接依据 Pi 原生事件。
- 不再先转换成旧事件名再 dispatch。

验收：

- 聊天主链路里不再依赖 `message.part.updated`、`question.asked` 这类旧事件名。

### 任务 5：重写聊天输入提交逻辑

要求：

- 聊天输入框直接走 Pi session prompt 提交流程。
- 不再以 OpenCode provider/model 前置条件阻塞发送。
- 不再把发送逻辑挂在旧的 session prompt_async 兼容思路上。

验收：

- 用户首次进入页面，在 Pi 可用时能直接发出第一条消息。

## M3：建立 Pi SDK 服务端宿主（P0）

目标：服务端用 Pi SDK 直接支撑前端，而不是通过桥接层支撑。

### 任务 6：新增 Pi SDK host

建议模块：

- `packages/web/server/lib/pi/sdk-host.js`
- `packages/web/server/lib/pi/session-registry.js`

职责：

- 创建和复用 `AgentSession`
- 管理 session 生命周期
- 接收用户 prompt
- 中断 session
- 维护交互请求状态

验收：

- 服务端能在无 RPC 子进程的情况下直接跑起 Pi session。

### 任务 7：直接暴露 Pi 原生语义 API

要求：

- 服务端 API 只服务当前前端，不再服务 OpenCode 兼容。
- SSE 或事件通道直接发送 Pi 原生语义数据。
- request/response 结构围绕 Pi 来设计，而不是围绕旧接口来设计。

验收：

- 新 API 不再出现明显的 OpenCode 风格字段和命名遗产。

### 任务 8：直接处理 extension UI request

要求：

- 服务端直接接住 Pi 的 extension UI request。
- 直接把 request 原始语义传给前端。
- 前端直接按 Pi request 类型渲染。
- 回复时也直接回 Pi 所需结构。

验收：

- `input/select/confirm` 在无桥接层的情况下闭环成功。

## M4：彻底删除历史代码（P1）

目标：把旧体系完全清走，避免长期双轨尸体残留。

### 任务 9：删除 OpenCode 服务端残留

包括但不限于：

- OpenCode 启动流程
- OpenCode proxy
- OpenCode health/restart/detection 逻辑
- `packages/web/server/lib/opencode/*`

### 任务 10：删除 Pi RPC bridge 残留

包括但不限于：

- `packages/web/server/lib/pi/runtime.js`
- `packages/web/server/lib/pi/bridge-schema.js`
- 所有 RPC envelope/parser/queue 逻辑

### 任务 11：删除前端 OpenCode 主链路残留

包括但不限于：

- `opencodeClient` 在聊天主链路中的使用
- OpenCode onboarding
- OpenCode 状态页
- 基于 OpenCode 事件名的核心处理逻辑
- 基于 OpenCode `Message/Part` 的主消息流

## 8. 首个 PR 应该做什么

下一个 PR 不要继续补 bridge，也不要继续修双 runtime。

建议只做以下几件事：

- 在文档和代码层明确冻结 OpenCode 与 RPC bridge 路线
- 盘点前端聊天主链路对 OpenCode 的强耦合点
- 新建 Pi SDK host 骨架
- 新建前端 Pi 原生状态骨架
- 停止让新功能进入 `opencodeClient`

这个 PR 的目标不是功能齐全，而是彻底纠正方向。

## 9. 第二个 PR 的目标

第二个 PR 才开始打通真正的 Pi 原生聊天闭环：

- Pi SDK session 创建
- 前端直接发 prompt
- 前端直接按 Pi 事件流更新消息
- 工具执行结果直接按 Pi 生命周期显示
- `input/select/confirm` 直接按 Pi request 闭环

## 10. 验收标准

### 架构验收

- [ ] 不再保留 OpenCode 运行时选项。
- [ ] 不再保留 Pi RPC 作为正式路线。
- [ ] 不再保留任何兼容层或翻译层作为长期设计。
- [ ] 前端与服务端都直接以 Pi 语义工作。

### 功能验收

- [ ] 用户不需要安装 OpenCode CLI。
- [ ] 应用启动不会再拉起 OpenCode。
- [ ] 用户进入聊天页即可直接以 Pi 发起对话。
- [ ] 基础消息、工具执行、交互请求都按 Pi 原生链路闭环。

### 代码结构验收

- [ ] 聊天主链路不再依赖 `opencodeClient`。
- [ ] 聊天主链路不再依赖 OpenCode `Message/Part`。
- [ ] 服务端不存在 Pi -> OpenCode 的桥接模块。
- [ ] 前端不存在 OpenCode -> Pi 或 Pi -> OpenCode 的兼容状态层。

## 11. 最终结论

后续开发不是“继续把 Pi 塞进旧系统”，而是：

- 删除 OpenCode
- 删除 bridge
- 删除翻译层
- 用 Pi SDK 重建服务端
- 用 Pi 原生语义重建前端

只有这样，方向才是对的。
