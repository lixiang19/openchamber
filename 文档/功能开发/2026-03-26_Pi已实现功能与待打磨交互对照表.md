# Pi 已实现功能 vs 仍待打磨交互 对照表

- 记录时间：2026-03-26
- 目的：把“已经能用的 Pi 功能”和“下一步仍该打磨的交互边界”拆开，避免把已落地能力误判成未实现，也避免把当前 UI 误判成最终态。
- 判定原则：
  - “已实现”只认当前代码。
  - “待打磨交互”只写当前代码/现有计划文档里能明确看出的边界，不写纯猜测。

## 2. 已实现且基本可视为“可用”的部分

这些能力当前不应再被表述成“还没做”：

- 流式消息输出
- 工具折叠与工具结果渲染
- task/subagent 摘要展示
- `/` 命令补全
- `@agent` 提及与发送链路解析
- question 工具交互卡片
- 模型选择、agent 选择
- 技能补全、文件 `@路径`

换句话说，当前阶段的主要问题已经不是“有没有”，而是“是不是最终态、是不是足够 Pi 原生”。

## 3. 仍待打磨的交互，不等于没实现

### 3.1 子 agent UI：已经有专门界面，但还不是最终形态

当前已经具备：

- 子任务摘要列表
- 子任务输出折叠
- 打开子任务入口
- 子任务触发的问题/权限在父会话上浮

但从现有方案文档看，当前目标一直是“先把基础 task/subagent 摘要显示稳定”，并没有承诺“完整复刻 Pi TUI 的专属交互层”。

所以这一项应描述为：

- **功能已实现**
- **交互仍有继续精炼空间**

### 3.2 question 工具：闭环已经有，但能力范围还偏聚焦

当前 question 卡片不是占位，而是可真正回答的交互。

但从现有计划文档看，当前更接近：

- 已经把 `input/select/confirm/question` 这类高频交互落好了
- 还不能直接等同于“Pi 全量扩展 UI 能力已经完整进入当前聊天界面”

所以这一项应描述为：

- **question 工具已实现**
- **更广义的扩展 UI / custom widget 还不是这套界面的完成态**

### 3.3 模型 / agent 选择：UI 很完整，但最终收口还要看 Pi 原生能力

当前从 UI 角度看，模型和 agent 选择器都已经很完整：

- 搜索
- 最近/收藏
- 变体切换
- 快捷键
- 会话内记忆
- 移动端入口

但现有 Pi 原生重构计划明确要求：

- 前端最终只能保留“Pi 真正存在且真实生效”的控制项
- 不能为了保留旧外观，把并不真实生效的控制项继续摆在主路径里

所以这一项应描述为：

- **当前 UI 已实现**
- **最终哪些控制项保留在主交互层，还需继续收敛**

### 3.4 `@agent`：能用，但当前更像“单点指定”而不是“复杂编排”

从 `parseAgentMentions()` 的代码看，当前解析逻辑会提取第一个有效 mention 作为发送时的 agent 目标。

这说明它已经不是“只做高亮”，而是真正参与发送链路；但也说明它当前更偏：

- 单个 agent 指定
- 快速切换执行对象

而不是：

- 多 agent 编排
- 一条消息里复杂的多目标路由

所以这一项应描述为：

- **`@agent` 已实现**
- **多 mention 复杂交互还不是当前重点**

## 4. 建议的对外表述方式

后面如果再写周报、迁移说明或 PR 描述，建议统一这么写：

### 4.1 可以直接说“已实现”的

- 流式对话
- 工具折叠
- 子 agent 摘要 UI
- `/` 命令
- `@agent`
- question 工具
- 模型选取
- agent 选取

### 4.2 更准确的说法应该是“已实现，但仍在打磨交互”的

- 子 agent 专门交互体验
- question/permission 的跨会话呈现
- 模型/agent 控件是否作为 Pi 原生主控制项长期保留
- `@agent` 的复杂编排能力
- 长会话下的流式稳定性与细节反馈

### 4.3 现在不适合说“已经完整覆盖”的

- 完整 Pi TUI 等级的子 agent 专属体验
- Pi 全量扩展 UI / custom widget 在当前聊天界面里的完整承接
- 所有控制项都已经完成 Pi 原生收口

## 5. 最终结论

一句话总结：

> 当前项目已经把 Pi 聊天主链路里最关键的一批可见功能做出来了，下一阶段的重点不是“补空白”，而是“把已经能用的能力打磨成真正 Pi 原生、边界更清楚的交互”。

因此，最准确的判断不是：

- “很多功能还没实现”

而是：

- “核心功能大多已实现，但其中一部分仍停留在可用版/过渡版交互，还没收敛成最终 Pi 原生体验。”
