# Pi 插件接入调研 方案

- 状态：草案
- 日期：2026-03-22
- Owner：AI / 待定
- 目标版本/里程碑：Pi 接入预研

## 1. 背景与问题

- 背景：希望 AI 服务不再接 OpenCode，而是改接 `pi`，同时继续保留当前项目的 OpenAurora Web 界面体验。
- 现象/痛点：当前项目的 Web/Desktop/VS Code 运行时都围绕 OpenCode 的 HTTP + SSE 契约构建；而 `pi` 尤其是 `pi-mono/packages/coding-agent` 更接近 agent runtime / RPC 宿主，`pi` 生态插件也主要运行在 Pi 自己的扩展/TUI 体系中。
- 成功定义：明确一条可落地路线，让 OpenAurora 作为 `pi` 的 Web 壳层，能逐步显示 `pi` 主会话与已安装插件的消息、工具结果以及必要的交互 UI。

## 2. 目标与非目标

- 目标：
  - 明确 `pi-coding-agent` 与当前 OpenAurora 的耦合边界和最小适配层。
  - 明确 `pi-subagents`、`pi-ask-user`、`@codexstar/pi-listen`、`glimpseui` 在“插件装在 Pi、Web 只接消息/UI 事件”的前提下分别能支持到什么程度。
  - 给出分阶段接入方案，区分“只接消息即可”与“必须接扩展 UI 请求”的能力边界。
- 非目标：
  - 本文不实现 `pi` 接入代码。
  - 本文不要求 OpenAurora 100% 复刻 Pi TUI 的所有原生交互细节。
  - 本文不讨论模型效果优劣，只讨论协议、产品能力和工程可行性。

## 3. 现状探索（Explorer）

- 入口与调用链：
  - `packages/ui/src/lib/opencode/client.ts:968` - UI 侧统一封装 OpenCode tools、question、permission、session 等 API；不是单纯 base URL，而是强依赖一整套 SDK 方法名。
  - `packages/ui/src/lib/opencode/client.ts:988` - 当前已具备 `permission.reply/list` 能力，说明项目已有“待确认工具执行”交互模型。
  - `packages/ui/src/lib/opencode/client.ts:1055` - 当前已具备 `question.reply/list` 能力，说明项目已有“结构化提问”交互模型。
  - `packages/ui/src/hooks/useEventStream.ts:1115` - UI 消费 `message.part.updated` 事件，并按 part 类型增量拼装消息。
  - `packages/ui/src/hooks/useEventStream.ts:1283` - UI 消费 `message.part.delta` 文本增量，说明当前消息流高度依赖 SSE 事件语义。
  - `packages/ui/src/hooks/useEventStream.ts:1365` - UI 消费 `message.updated`，并据此修正用户消息、agent 选择、状态等派生数据。
  - `packages/ui/src/components/chat/message/parts/ToolPart.tsx:763` - UI 已能把 `task/subagent` 一类工具输出渲染成时间线式摘要，适合承接 `pi-subagents` 的工具消息。
  - `packages/ui/src/components/chat/message/parts/ToolPart.tsx:791` - 已识别 `subagent_type` 之类的输入元信息，说明子代理类消息已有展示基础。
  - `packages/ui/src/components/chat/QuestionCard.tsx:16` - 已有内联问题卡片，可承接类似 `ask_user` 的结构化提问结果或后续 Web 侧答题 UI。
  - `packages/ui/src/components/chat/PermissionCard.tsx:59` - 已有权限确认卡片，可映射 Pi 扩展/UI 请求中的确认类动作。
  - `packages/web/server/index.js:6631` - Web server 当前将 `/api/event`、`/api/global/event` 直接转发给 OpenCode。
  - `packages/web/server/index.js:6722` - 除少量本地 API 外，大多数 `/api/*` 请求最终也是代理到 OpenCode。
- 关键数据结构/状态：
  - 消息层核心依赖 `Session / Message / Part / ToolPart`；其中 message part 的增量更新和最终合并都在前端完成。
  - 待处理交互已分成两类：`QuestionRequest` 与 `PermissionRequest`，前者偏结构化问答，后者偏执行授权。
  - 子代理显示并不要求前端理解完整编排器，只要会话里能收到稳定的工具消息、结果文本和 session 关联元数据即可。
- 约束与坑点：
  - 当前前端事件语义是 OpenCode 风格，不能直接消费 `pi` RPC 原始事件，必须做翻译层。
  - 当前 Web server 本质是 OpenCode 代理；若改接 `pi`，要么模拟现有 `/api/* + SSE` 契约，要么大改前端 client。
  - `pi` 插件很多能力不是“会话消息”，而是 `ctx.ui.*` 扩展 UI 请求；只接消息并不能完整覆盖所有插件体验。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `pi-mono/packages/coding-agent` 提供的核心是 SDK + RPC 宿主，不是现成的 OpenCode 式 HTTP/SSE server。关键文件包括 `packages/coding-agent/src/core/sdk.ts`、`packages/coding-agent/src/core/agent-session.ts`、`packages/coding-agent/src/modes/rpc/rpc-mode.ts`、`packages/coding-agent/src/modes/rpc/rpc-types.ts`。
  - `pi` 的 RPC 能力至少可分三层：普通消息/工具事件、custom message、extension UI request。OpenAurora 若只接第一层，可较快跑通聊天与工具展示；若想更完整支持插件，还需逐步补后两层。
  - `pi-subagents` 的核心编排逻辑都在 Pi 扩展侧；它注册 `subagent` 工具和 slash 命令，Web 不需要自己实现编排，只需能显示其工具调用、输出结果，以及后续可选支持 custom message / widget / status。
  - `pi-ask-user` 注册的是 `ask_user` 工具；如果在 Pi TUI 中完成提问，Web 只需要显示最终 tool result 即可。如果希望用户直接在 Web 回答，就必须接 `input/select/custom overlay` 一类扩展 UI 请求。
  - `@codexstar/pi-listen` 严重依赖 `setStatus`、`setWidget`、`setEditorText`、命令注册和本地录音流程；只接消息时只能看到最终提交出去的用户文本，无法天然复刻录音中状态、设置面板和实时转写体验。
  - `glimpseui`/`glimpse companion` 更接近原生 companion 浮窗，不是聊天消息插件；它对 Web 壳层的价值主要是产品形态参考，而不是消息协议适配对象。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：保留当前仓库与界面，在 `packages/web/server/` 内新增 `pi` 适配层，把 `pi-coding-agent` 的 RPC / SDK 结果翻译为 OpenAurora 现有的消息、工具、问题与权限模型，分阶段补齐插件所需的 UI 事件。
- 取舍：这样做能最大化保留现有 UI、路由、Settings、Desktop/VS Code 壳层和消息渲染能力；代价是需要在 server 侧维护一层 `pi -> OpenAurora` 协议映射。
- 影响面：主要影响 `packages/web/server/` 的运行时适配、`packages/ui/src/lib/opencode/client.ts` 的上游接口来源、以及 `packages/ui/src/hooks/useEventStream.ts` 所消费的事件语义。

### 5.2 风险与回滚

- 风险：
  - `pi` 插件的很多高级体验来自扩展 UI，而不是标准消息：缓解措施是按层分阶段交付，先跑通“消息可见”，再补“交互可用”。
  - `pi-listen` 与 `glimpse` 这类插件大量依赖 Pi TUI / 原生能力：缓解措施是接受“Web 只支持部分体验”，不要在第一阶段承诺全量一致。
  - `pi-subagents` 可能输出 custom message 或 session 侧带元数据：缓解措施是先保留原始结果文本，必要时再为 custom message 单独建展示层。
- 回滚：
  - 保留现有 OpenCode 代理路径，通过运行时开关切回 OpenCode。
  - 适配层独立为 `pi` provider/runtime，不替换现有 UI 组件结构，失败时可快速切回原后端。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：
  - 用户在 OpenAurora Web 中发送消息。
  - Web server 将请求发给 `pi-coding-agent` 会话。
  - `pi` 产生普通消息、工具事件、问题/确认或扩展 UI 请求。
  - 适配层将其翻译成现有前端能消费的 SSE / API 语义。
  - 前端继续用现有消息列表、ToolPart、QuestionCard、PermissionCard 等组件展示。
- 边界条件：
  - 若插件只输出普通消息与工具结果，则无需额外 UI 适配。
  - 若插件依赖 `custom message`，Web 至少要保留 custom payload 并渲染基础结果。
  - 若插件依赖 `setStatus`、`setWidget`、`setEditorText`、`custom overlay` 等扩展 UI，请求未接入前只能降级展示结果，不能视为“完整支持”。

### 6.2 接口与契约

- API/函数签名：
  - `POST /api/session/:id/prompt` 或等价入口：Web -> `pi` 发送用户 prompt。
  - `GET /api/event` / `GET /api/global/event`：server 把 `pi` 消息事件转换为前端现有可消费的 SSE 事件。
  - `GET /api/questions` / `POST /api/question/reply`：映射 Pi 中的交互式问题请求。
  - `GET /api/permissions` / `POST /api/permission/reply`：映射 Pi 中的确认/授权请求。
  - `GET /api/messages`：必要时将 `pi` 会话消息历史转换为 OpenAurora 消息结构。
- 错误码/异常：
  - `pi` 会话启动失败：返回明确 server/runtime unavailable，不做静默兜底。
  - 收到未知的扩展 UI 请求：记录日志并以 unsupported UI request 明确暴露，而不是悄悄吞掉。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - 消息层最少需要：`sessionId`、`messageId`、`role`、`parts[]`、`tool state`、`timestamps`。
  - custom message 最少需要：`customType`、`content`、`details`，便于对接 `pi-subagents` 这类扩展返回。
  - 扩展 UI 请求最少需要：`kind`、`payload`、`requestId`、`sessionId`、`reply channel`。
- 迁移策略：
  - 初期保留现有前端 store 结构，只在 server 层做翻译。
  - 若后续 `pi` 事件模型差异过大，再考虑抽离一层中立消息协议。

### 6.4 兼容性与发布

- 兼容策略：保留 OpenCode 与 Pi 双运行时，优先通过配置切换；在 Pi 模式下逐步声明插件支持等级。
- 发布步骤：
  - 第一步发布“基础聊天 + 工具消息展示”。
  - 第二步发布“custom message + 问题/确认桥接”。
  - 第三步再按需发布“扩展 UI 请求支持”。

### 6.5 可观测性

- 日志：记录 `pi` 原始事件、翻译后的 SSE 事件、未支持的扩展 UI 请求、tool/custom message 映射失败原因。
- 指标：消息事件数、映射失败数、交互请求数、Web 可承接率、插件类型覆盖率。
- 告警：当未知事件类型或未知扩展 UI 请求连续出现时提示协议漂移风险。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] 文档明确区分“普通消息/工具结果”、“custom message”、“extension UI request”三层能力，并说明对应支持范围。
  - [ ] 文档明确给出 4 个插件的支持判断，不再把“插件编排逻辑”错误归到 OpenAurora Web 层。
- 非功能验收：
  - [ ] 性能：方案默认不要求前端大改协议消费层，优先在 server 适配层收敛复杂度。
  - [ ] 可靠性：对未知 UI 请求和未知事件有显式失败或降级策略，不做静默吞错。
  - [ ] 安全：插件仍运行在 `pi` 侧，Web 不新增越权执行逻辑。

## 8. 里程碑与任务（Milestones）

> 原则：只拆 1-3 个里程碑；每个里程碑都必须有可验证的交付物与退出标准。里程碑内再列任务，但不要过度细碎。

### M1：跑通 Pi 基础消息层

- 交付物：OpenAurora Web 能显示 `pi-coding-agent` 的用户消息、assistant 消息、工具调用和工具结果。
- 退出标准：`pi-subagents` 在不依赖额外扩展 UI 的情况下，其主要工具消息和输出结果可在 Web 端被看到。
- 任务：
  - [ ] 在 server 层建立 `pi event -> OpenAurora SSE` 映射（文件/模块：`packages/web/server/`）验收：普通消息和 tool result 可显示。
  - [ ] 复用现有 `ToolPart`/消息列表渲染承接 `subagent` 相关工具输出（文件/模块：`packages/ui/src/components/chat/message/parts/ToolPart.tsx`）验收：子代理输出可读且 session 关联清晰。

### M2：补齐 custom message 与结构化交互

- 交付物：OpenAurora Web 能显示 `pi-subagents` 的 custom message，并支持 `pi-ask-user` 的结果展示或最小交互桥接。
- 退出标准：`pi-subagents` 和 `pi-ask-user` 在 Web 里都至少达到“结果可见、流程不断”的状态。
- 任务：
  - [ ] 扩展消息模型支持 `customType/details`（文件/模块：消息 store、message renderer）验收：custom result 不丢字段。
  - [ ] 将 Pi 的问答/确认请求映射到现有 `QuestionCard`/`PermissionCard`（文件/模块：`packages/ui/src/components/chat/QuestionCard.tsx`、`packages/ui/src/components/chat/PermissionCard.tsx`）验收：Web 端可应答或至少清楚展示未支持状态。

### M3：按需支持扩展 UI 请求

- 交付物：支持最有价值的扩展 UI 请求，如 `input/select/confirm`、`setStatus`、`setWidget`，并明确哪些插件达到“完整可用”。
- 退出标准：`pi-ask-user` 在 Web 中可直接交互；`pi-listen` 至少有状态显示策略；`glimpse` 明确标记为 desktop 原生能力或不支持。
- 任务：
  - [ ] 建立 extension UI request 映射表与 reply 通道（文件/模块：`packages/web/server/` + UI overlay）验收：至少支持 `input/select/confirm`。
  - [ ] 决定 `setEditorText`、`setStatus`、`setWidget` 在 Web 中的映射策略（文件/模块：chat input / status UI）验收：对 `pi-listen` 的支持边界有明确产品定义。

## 9. 执行计划与闭环

- 执行顺序：M1 -> M2 -> M3
- 每个里程碑验证：
  - M1：用装有 `pi-subagents` 的 Pi 会话做一次真实 prompt，检查消息、tool part、subagent 输出是否在 Web 中可见。
  - M2：触发 `ask_user` 与 `subagent` custom result，检查结果是否显示且流程不中断。
  - M3：触发 `input/select/confirm/setStatus/setWidget/setEditorText`，逐项验证已支持与未支持路径是否符合预期。
- 最终回报：变更摘要 + 插件支持矩阵 + 已支持/未支持扩展 UI 列表 + 风险残留 + 下一步。
