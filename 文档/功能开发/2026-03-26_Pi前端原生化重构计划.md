# 2026-03-26 Pi前端原生化重构计划

## 背景

当前 `packages/ui` 前端虽然已经开始接入 Pi runtime，但整体数据模型仍深度依赖旧的 `@opencode-ai/sdk/v2` / `@opencode-ai/sdk/v2/client` 类型与接口形状。现状本质上是：

- 底层部分能力已经切到 Pi
- 前端主数据模型仍然是 OpenCode 语义
- `runtime client` 仍承担大量 `Pi -> 旧 UI 结构` 的兼容投影工作

这不符合本项目当前的迁移目标：

- **真正迁移到 Pi**，不是“底层换了，前端仍活在 OpenCode 世界里”
- **不做兼容层长期保留**，要从根上替换前端数据模型
- **UI 一点都不要删除**，现有界面、交互入口、聊天呈现能力都要保留

## 顶级原则

### 1. 不删除 UI

本次重构的目标是**替换前端数据模型和运行时接入方式**，不是删减功能。

必须坚持：

- 现有页面结构保留
- 现有聊天界面保留
- 现有工具结果展示保留
- 现有权限请求 UI 保留
- 现有问题提问 UI 保留
- 现有会话列表、消息列表、输入框、侧栏、设置页都保留

允许做的事情：

- 调整组件输入类型
- 调整状态来源
- 调整事件归并逻辑
- 重写内部 mapper / reducer / store
- 在保持视觉和交互大体不变的前提下重构实现

不允许做的事情：

- 因为 Pi 当前没有某个能力，就把前端对应 UI 删掉
- 因为迁移麻烦，就把现有聊天能力砍掉一部分
- 把“暂时做不到”包装成“产品不需要”

### 2. 前端对话功能全盘保留

此次重构必须保留前端当前对话体系的完整目标，而不是只保留最小聊天流。

这里的“全盘保留”包括但不限于：

- 用户消息
- assistant 文本流式输出
- reasoning / thinking 展示
- tool call 展示
- tool result 展示
- question 请求展示
- permission 请求展示
- session 状态展示
- 目录上下文、附件、mention 等既有对话输入能力

注意：

- 当前某些能力在 Pi runtime 里还没有现成等价实现
- 这**不代表前端可以删除这些能力**
- 正确策略是：**前端先保留能力边界，后续由 Pi 自定义扩展来对齐**

### 3. Pi 暂缺能力不删除，只标记为待对齐

如果现阶段 Pi 没有直接对齐的能力，例如：

- permission 请求
- 某类特定 UI request
- 某类 session 级别控制能力

则原则如下：

- **这一次不删除前端**
- **这一次不伪装兼容**
- **这一次明确记为“Pi extension 对齐项”**

也就是说：

- 前端能力边界先保留
- 数据模型先按最终目标设计
- 缺失的底层能力以后通过 Pi 自定义扩展补齐

本次不做：

- 为了先跑通而临时删除 UI
- 为了先跑通而继续保留 OpenCode 兼容协议
- 为了先跑通而把 Pi 请求硬翻译成旧 OpenCode 私有事件体系并长期保留

### 4. 前端原生语义必须按 Pi 重建

既然要真正迁移，就必须承认：

- 前端不能继续以 `Session / Message / Part / Agent / Provider` 的 OpenCode SDK 世界观为基础
- 前端应该直接建立在 Pi 原生语义上
- UI 层看到的是**前端自己的 Pi 领域模型**，不是旧 SDK 类型

因此本次重构方向不是：

- `Pi -> OpenCode 类型`

而是：

- `Pi runtime 原始事实 -> 前端 Pi 领域模型`

## 目标

### 总目标

删除 `@opencode-ai/sdk/v2/client` 在 `packages/ui` 中的依赖，把前端核心类型系统和 runtime 访问层改造成 **Pi 原生前端架构**。

### 子目标

1. 前端建立独立的 Pi 原生类型层
2. `runtime client` 不再依赖 OpenCode SDK client
3. 所有 store 不再依赖旧 SDK 类型
4. 聊天消息渲染层改为消费 Pi 原生前端模型
5. 会话、agent、provider、question、permission 都改成 Pi 原生模型
6. UI 完整保留，不因 Pi 暂缺能力而删除
7. 最终删除 `@opencode-ai/sdk/v2/client` 在 `packages/ui` 内部的使用

## 非目标

本轮**不做**以下内容：

- 不新增产品功能
- 不重做视觉设计
- 不删减前端对话能力
- 不在本轮补完所有 Pi 扩展能力
- 不把 permission / question 的最终扩展协议一次性做完
- 不处理与本次目标无关的其他 OpenCode 历史残留
- 不在本轮重构 VSCode 扩展端

## 核心设计

## 一、前端新的领域模型

需要新建 `packages/ui/src/lib/runtime/types.ts`，作为前端**唯一正式 runtime 类型层**。

这套类型的原则：

- 命名和语义以 Pi 为基础
- 仅服务当前前端需求
- 允许适量展示型派生字段
- 禁止出现 OpenCode SDK 类型影子

建议核心类型：

- `RuntimeSession`
- `RuntimeMessage`
- `RuntimeContentBlock`
- `RuntimeAssistantMessage`
- `RuntimeToolExecution`
- `RuntimeInteractiveRequest`
- `RuntimeAgent`
- `RuntimeProvider`
- `RuntimeModel`
- `RuntimeQuestionRequest`
- `RuntimePermissionRequest`

其中：

- `RuntimeMessage` 要直接表达 Pi 的角色与内容块
- `RuntimeContentBlock` 要覆盖 `text/thinking/image/toolCall/...`
- `RuntimeInteractiveRequest` 要成为 question / permission / 未来扩展 UI 的统一前端入口

## 二、runtime client 改成真正的 Pi client

当前 `packages/ui/src/lib/runtime/client.ts` 仍然是旧 OpenCode 形状的 runtime facade。

最终目标：

- 不再 import `createOpencodeClient`
- 不再依赖 `OpencodeClient`
- 不再返回旧 SDK client 形状
- 改成纯 `fetch + EventSource + Runtime types`

职责只保留：

- Pi HTTP 调用
- Pi SSE 订阅
- 目录上下文管理
- 基于 Pi 事件的状态输入

不再保留：

- 伪造旧 `session.*` SDK 接口
- `Pi -> OpenCode Agent/Session/Message/Part` 映射
- 任何旧 SDK 类型导出

## 三、聊天系统直接消费 Pi 原生消息模型

现有聊天系统大量基于 `Message + Part`。

重构后：

- assistant 消息直接消费 `RuntimeMessage.content[]`
- tool execution 用独立 execution 状态展示
- question / permission 用独立 interactive request 状态展示
- 不再把所有能力硬塞进旧 `Part` 概念

这意味着：

- 消息渲染组件要适配新的 `RuntimeContentBlock`
- timeline / grouped rendering / turn overlay 逻辑要按新模型重写
- 现有视觉表现尽量保留，但其输入类型要彻底替换

## 四、question / permission 前端能力完整保留

这是本次重构的关键约束。

### question

- 前端 UI 保留
- 前端状态模型保留
- 继续存在用户答复链路
- 底层直接接 Pi interactive request

### permission

- 前端 UI 保留
- 不因 Pi 当前未完全对齐而删除
- 本轮可以先保留前端模型和渲染入口
- 后续通过 Pi 自定义扩展来补齐真实 permission 请求协议

因此需要把 `RuntimeInteractiveRequest` 设计成能覆盖：

- 已实现的 Pi question
- 当前前端已有的 permission UI
- 后续通过 Pi extension 接入的 permission / widget / status request

## 五、settings / agents / providers 页面全部改用 runtime 模型

包括但不限于：

- agent 页面
- provider 页面
- 配置刷新入口
- runtime 状态相关入口

目标是：

- UI 层不再 import 旧 SDK 类型
- 页面逻辑不再面向 OpenCode 配置模型
- agent / provider / session 等设置页统一围绕 Pi runtime 设计

## 分阶段实施方案

## 阶段 0：约束确认（本文件）

完成内容：

- 明确 UI 不删除
- 明确对话功能全保留
- 明确 Pi 暂缺能力以后走 extension，不在本轮删除前端
- 明确彻底删除旧 SDK client 的目标

## 阶段 1：建立新类型地基

输出：

- `packages/ui/src/lib/runtime/types.ts`
- `packages/ui/src/lib/runtime/events.ts`（如需要）
- `packages/ui/src/lib/runtime/contracts.ts`（如需要）

任务：

- 定义 session/message/content/agent/provider/question/permission 的 Runtime 类型
- 明确哪些字段是事实字段，哪些字段是展示型派生字段
- 停止在新代码里引用 `@opencode-ai/sdk/v2` 类型

验收标准：

- 前端存在独立、完整的 Pi 原生类型层
- 新类型层不依赖旧 SDK

## 阶段 2：重写 runtime client

输出：

- 重写 `packages/ui/src/lib/runtime/client.ts`

任务：

- 去掉 `createOpencodeClient`
- 改为纯 Pi API client
- 改为纯本地 Runtime types 出参
- 保留目录上下文、SSE、session 操作、question/permission 响应等能力

验收标准：

- `runtime/client.ts` 不再 import `@opencode-ai/sdk/v2/client`
- 对外只暴露 Pi 原生 runtime 语义

## 阶段 3：替换 store 层

重点文件：

- `packages/ui/src/stores/useSessionStore.ts`
- `packages/ui/src/stores/messageStore.ts`
- `packages/ui/src/stores/sessionStore.ts`
- `packages/ui/src/stores/useConfigStore.ts`
- `packages/ui/src/stores/useAgentsStore.ts`
- `packages/ui/src/stores/permissionStore.ts`
- `packages/ui/src/stores/questionStore.ts`

任务：

- 让所有 store 依赖 Runtime types
- 删除对旧 SDK `Session/Message/Part/Agent/Provider` 的依赖
- 让 store 状态机直接消费 Pi event / session snapshot

验收标准：

- store 层不再依赖旧 SDK 类型
- state shape 只围绕 Pi runtime 模型

## 阶段 4：替换聊天渲染层

重点区域：

- chat message
- message parts
- assistant streaming
- tool result 渲染
- question / permission 渲染
- timeline / turn grouping

任务：

- 把基于旧 `Part` 的逻辑替换成基于 `RuntimeContentBlock`
- 保留现有视觉表现与交互细节
- 删除旧 part projector / adapter 逻辑

验收标准：

- 聊天 UI 外观和能力保留
- 输入数据已完全切到 Pi 原生前端模型

## 阶段 5：替换页面和辅助模块

包括：

- agent 页面
- provider 页面
- session sidebar
- files / search / multirun / mcp / todo 等依赖旧 SDK 类型的页面和 hooks

验收标准：

- `packages/ui` 内部不再引用旧 SDK 类型

## 阶段 6：删除旧依赖

任务：

- 删除 `packages/ui` 内部所有 `@opencode-ai/sdk/v2` / `@opencode-ai/sdk/v2/client` import
- 清理相关 alias / 构建配置
- 若已无引用，再从依赖声明中移除

验收标准：

- `packages/ui` 中不再存在旧 SDK client 依赖

## 关键风险

### 风险 1：聊天渲染层耦合过深

旧的 `Message + Part` 假设已经渗透到很多组件。

对策：

- 先立新类型层
- 再统一替换，不做长期双轨并存

### 风险 2：UI 功能被误删

因为 Pi 暂时缺某些能力，开发过程中容易“先删掉再说”。

对策：

- 本文明确禁止
- 前端入口保留
- 缺能力记录为 extension 对齐项

### 风险 3：一次性切换范围极大

这次重构会波及大量文件。

对策：

- 先定统一 Runtime 领域模型
- 以模型替换为中心推进，而不是零散修 import

## Pi 扩展对齐项（本轮不做）

以下能力即使 Pi 当前未完成，也不能删前端：

- permission request
- 更丰富的 interactive UI request
- 某些细粒度 session 控制能力
- 可能存在的扩展 widget/status/editor request

这些能力的后续策略是：

- 以前端最终需求为准保留 UI
- 以后通过 Pi 自定义扩展补齐协议
- 不再引入旧 OpenCode 协议做兼容桥接

## 验收标准

本次 Pi 前端原生化重构完成时，应满足：

1. `packages/ui` 不再依赖 `@opencode-ai/sdk/v2/client`
2. 前端核心类型不再使用旧 SDK `Session/Message/Part/Agent/Provider`
3. 前端聊天 UI、question UI、permission UI、tool UI 保持存在
4. 现有对话主链路能力保留
5. runtime client 成为 Pi 原生 client
6. 不存在 `Pi -> OpenCode 类型` 的长期兼容投影层

## 结论

这不是一次“改 import”的工作，而是一次前端核心领域模型重建。

但必须坚持两个底线：

- **真正切到 Pi，不保留旧类型兼容层**
- **UI 一点不删，对话功能全盘保留；Pi 暂缺能力以后通过扩展补齐**
