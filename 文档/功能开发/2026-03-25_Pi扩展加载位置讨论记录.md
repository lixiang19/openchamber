# Pi 扩展加载位置讨论记录

- 状态：已记录
- 日期：2026-03-25
- 类型：讨论结论 / 仅记录，不含实现
- 适用范围：当前项目的 Pi Web/Node 宿主接入方案

## 1. 讨论背景

本次讨论的核心问题不是“Pi 扩展应该写在仓库里还是写在用户的 `~/.pi/agent/extensions/` 里”这么简单，而是更具体的问题：

- 如果当前项目要把某些 Pi 扩展能力作为产品能力交付给最终用户，是否必须要求用户自己去其电脑上的 `~/.pi/agent/extensions/` 安装插件？
- 这些扩展能不能直接写在当前项目的 Node 宿主层里，由项目运行时主动加载？

## 2. 讨论结论

结论明确如下：

- 可以写在当前项目的 Node 宿主层里。
- 如果扩展能力是当前产品的一部分，就不应该依赖用户自己去 `~/.pi/agent/extensions/` 安装。
- 用户是否在自己电脑上装过全局 Pi 扩展，不应成为当前项目功能是否可用的前提。
- 对当前项目而言，更合理的方式是：把扩展作为项目内置资源，由服务端宿主显式加载。

一句话结论：

> 给“本项目的产品用户”使用的 Pi 扩展，应当由本项目内置并在 Node 宿主中加载，而不是要求用户手动安装到 `~/.pi/agent/extensions/`。

## 3. 为什么可以这么做

依据 Pi 官方 SDK/扩展机制，本项目作为 Pi 的宿主程序，可以自行决定资源加载方式。

### 3.1 官方能力边界

Pi SDK 的 `createAgentSession()` 不是只能依赖默认自动发现；它的资源来源由 `ResourceLoader` 决定。

可用方式包括：

- 直接使用默认发现逻辑
- 使用 `DefaultResourceLoader` 并通过 `additionalExtensionPaths` 注入扩展路径
- 使用 `extensionFactories` 注入宿主内联扩展
- 自定义 `ResourceLoader`，完全接管扩展、skills、prompts、themes、AGENTS 等资源来源

这意味着：

- 扩展不一定非要存在于用户 `~/.pi/agent/extensions/` 中
- 扩展可以位于当前项目仓库内部
- 扩展也可以根本不以“磁盘上单独插件目录”的形式存在，而是直接由当前项目的 Node 代码注册

## 4. 三种加载方式的区别

### 4.1 用户全局目录

位置示例：

- `~/.pi/agent/extensions/`

特点：

- 面向用户自己的原生 Pi CLI 环境
- 对所有项目生效
- 适合个人习惯型、跨项目复用型扩展
- 不适合作为当前产品能力的正式依赖

问题：

- 用户未安装时，功能缺失
- 不同用户环境不一致，难以复现和排障
- 产品能力被外部个人环境污染

### 4.2 仓库内标准 Pi 目录

位置示例：

- `.pi/extensions/`

特点：

- 仍然属于项目内资源
- 可以随仓库一起版本管理
- 对团队协作和项目复现更友好
- 但本质上仍在沿用 Pi 的默认资源发现体系

适用场景：

- 该扩展也希望在“用户直接打开项目目录运行 Pi”时被自然发现
- 希望保留 Pi 原生目录约定

### 4.3 当前项目的 Node 宿主内置加载

位置示例：

- `packages/web/server/lib/pi/extensions/...`
- 或直接在宿主代码里通过 `extensionFactories` 注册

特点：

- 扩展能力直接成为当前产品运行时的一部分
- 用户无需关心 Pi 全局目录
- 最符合“这是产品内建能力，不是用户自行安装插件”的定位
- 可由服务端控制版本、启用顺序、隔离策略与错误处理

这是本次讨论认为最适合当前项目的方向。

## 5. 当前项目现状

当前项目的 Pi 宿主实现，现阶段仍然是直接：

- 在 `packages/web/server/lib/pi/sdk-host.js` 中调用 `createAgentSession({ cwd: normalizedCwd })`

这意味着当前仍主要依赖 Pi 的默认发现机制。

因此现状是：

- 项目目录下若存在 `.pi/extensions/`，会被发现
- 用户全局 `~/.pi/agent/extensions/` 里的扩展，也可能被发现
- 当前项目尚未把“只加载项目内置扩展、忽略用户全局扩展”这件事彻底收口

所以要实现本次讨论想要的效果，不能只停留在“把文件放哪里”的层面，而要改宿主加载策略。

## 6. 若要达成目标，需要什么设计

目标是：

- 产品自带某些 Pi 扩展能力
- 用户无需自己安装到 `~/.pi/agent/extensions/`
- 最终运行结果不被用户全局 Pi 环境影响

要达到这个目标，应采用下面的宿主设计：

### 6.1 基本方案

由当前项目的 Node 宿主显式加载项目内置扩展，例如：

- 使用 `DefaultResourceLoader({ additionalExtensionPaths: [...] })`
- 或使用 `DefaultResourceLoader({ extensionFactories: [...] })`

这样即使用户没有在全局目录安装插件，当前产品依然可以使用这些扩展能力。

### 6.2 更彻底的方案

如果还要避免用户全局扩展污染当前产品行为，则不应继续完全依赖默认发现。

更彻底的方向是：

- 自定义 `ResourceLoader`
- 或以“full control”方式只暴露项目明确允许的扩展/skills/prompts/context

这样可以确保：

- 当前产品只加载项目自带资源
- 用户自己的 `~/.pi/agent/extensions/` 不再影响产品运行结果

## 7. 对当前项目的建议

本次讨论形成的建议如下：

- 对“属于当前产品功能”的 Pi 扩展，不要要求用户自行安装到 `~/.pi/agent/extensions/`
- 应把这类扩展收敛到当前仓库或当前服务端运行时中
- 运行时由当前项目的 Node 宿主显式加载这些扩展
- 后续若需要环境一致性和更强可控性，应进一步收口到自定义 `ResourceLoader`
- 不应让产品正式能力依赖用户个人 Pi 环境

## 8. 本次讨论不包含的内容

本记录只确认方向，不包含以下动作：

- 不修改当前代码
- 不调整 `sdk-host.js`
- 不实现 `ResourceLoader` 收口
- 不新增项目内置扩展目录
- 不处理扩展 UI 完整兼容问题

换句话说，本文只是把结论记录下来，供后续真正实施时作为依据。

## 9. 后续实施时的判断标准

后续若进入实现阶段，可按下面标准判断资源应该放在哪里：

- 若这是当前产品必须具备的能力：放项目内，由宿主加载
- 若这是个人跨项目习惯工具：放用户全局 `~/.pi/agent/extensions/`
- 若希望项目目录可被原生 Pi 自然发现：可放 `.pi/extensions/`
- 若希望彻底避免用户环境污染：使用自定义 `ResourceLoader` 明确收口

## 10. 最终一句话

当前项目要交付给用户的 Pi 扩展能力，可以也应该内置在项目的 Node 宿主层中；不应把正式产品能力建立在用户手动维护 `~/.pi/agent/extensions/` 的前提上。
