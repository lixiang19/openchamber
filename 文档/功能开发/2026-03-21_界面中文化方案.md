# 界面中文化方案

- 状态：草案
- 日期：2026-03-21
- Owner：Codex（草拟）
- 目标版本/里程碑：packages/ui 第一阶段中文化

## 1. 背景与问题

- 背景：当前 OpenAurora UI 以英文硬编码文案为主，用户希望界面上的英文统一改成汉字。
- 现象/痛点：文案分散在设置元数据、侧边栏常量和各类 React 组件内，当前仓库未接入现成 i18n 机制，后续维护和扩展成本高。
- 成功定义：`packages/ui` 中用户可见界面默认显示中文，且后续新增文案必须通过统一字典层接入。

## 2. 目标与非目标

- 目标：
  - 为 `packages/ui` 建立统一的前端文案字典与访问入口，支持默认中文。
  - 在不改变既有 slug、路由、配置键和业务标识的前提下，完成首批界面中文化。
  - 建立可持续迁移路径，避免后续继续新增硬编码英文文案。
- 非目标：
  - 本阶段不处理 CLI 输出、服务端日志、协议字段、模型名、供应商名等非界面展示文本。
  - 本阶段不强制处理 `packages/vscode` 与 `packages/web/bin/cli.js` 的全部交互文案，除非它们直接复用 `packages/ui`。

## 3. 现状探索（Explorer）

- 入口与调用链：
  - `packages/ui/src/main.tsx:91` - UI 根节点挂载位置，适合注入全局 `I18nProvider`。
  - `packages/ui/src/App.tsx:97` - UI 根组件入口，适合作为全局语言能力的消费上游。
  - `packages/ui/src/components/views/SettingsView.tsx:167` - 设置首页直接硬编码标题、卡片标题和说明文案。
- 关键数据结构/状态：
  - `packages/ui/src/lib/settings/metadata.ts:40` - 设置页元数据类型定义，`title`/`description` 当前直接使用展示字符串。
  - `packages/ui/src/lib/settings/metadata.ts:50` - 设置分组标签集中定义，适合第一批抽离为翻译 key。
  - `packages/ui/src/lib/settings/metadata.ts:61` - 设置页面标题和搜索关键词集中定义，既涉及显示文案也涉及设置页搜索体验。
  - `packages/ui/src/constants/sidebar.ts:9` - 侧边栏配置结构包含 `label` 与 `description`，是导航中文化的核心入口。
  - `packages/ui/src/constants/sidebar.ts:16` - 侧边栏导航项当前全部英文硬编码。
- 约束与坑点：
  - 当前仓库未发现 `i18n`、`locale`、`translations`、`react-intl`、`i18next` 等既有国际化机制。
  - `slug`、section id、设置 key 属于内部稳定标识，不能随中文化一起翻译。
  - 设置页搜索依赖 `keywords`；若仅把展示文案改成中文，会影响英文搜索习惯，需要明确是否保留双语关键词。
  - 文案广泛散落于 `packages/ui/src/components/sections/`、`packages/ui/src/components/chat/`、`packages/ui/src/components/session/`，不能只改集中配置文件。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `react-i18next` + `i18next` 是 React/Vite 项目最常见的增量国际化方案，支持逐步替换硬编码文案；官方入口：`react.i18next.com/latest/using-with-hooks`。
  - 若近期只需默认中文，不急于运行时切多语言，自定义轻量 Provider 也能满足需求，但未来切换多语言时会有二次迁移成本。
  - 缺失翻译处理不应静默回退英文；开发期应尽早暴露缺 key，避免“用户仍看到英文”掩盖漏改问题。
  - key 设计应采用语义化命名空间，如 `settings.home.title`、`sidebar.sessions.description`，避免使用英文原文或无语义编号作为 key。
  - 如未来要支持语言切换，标准 `i18next` 方案迁移更顺；若本阶段目标是“先全部中文化”，可先固定 `zh-CN`，保留后续扩展能力。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：在 `packages/ui` 内引入一层轻量、强约束的前端文案系统，默认只启用 `zh-CN` 字典，并将界面硬编码文案逐步迁移到语义化 key。
- 取舍：不直接引入完整 `react-i18next` 依赖，而是先落地自定义 `I18nProvider + useI18n + zh-CN 字典`；这样改动更小、接入更快、对“全部改中文”目标最直接，同时保留未来平滑升级到标准库的接口形态。
- 影响面：`packages/ui/src/main.tsx`、导航与设置元数据、设置页、聊天页、会话页及各 section 子组件中的所有用户可见文本。

### 5.2 风险与回滚

- 风险：
  - 漏改文本仍显示英文：通过“缺 key 抛错/报警 + 目录分批扫描 + 人工验收”缓解。
  - key 命名混乱导致后期维护困难：通过按模块命名空间和字典文件分层缓解。
  - 搜索体验退化：设置页 `keywords` 保留双语关键词，展示文案中文化但搜索兼容中英文。
  - 后续多语言扩展成本：Provider 和 `t()` 设计对齐标准 i18n 接口，未来可替换底层实现。
- 回滚：
  - 代码级回滚：逐文件回退到改造前版本即可，不涉及数据迁移。
  - 结构级回滚：若轻量实现不满足需求，可保留 key 与字典结构，仅将 Provider/Hook 替换为 `react-i18next` 实现。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：应用启动后默认加载中文文案；页面渲染时所有用户可见文本通过统一 `t(key)` 获取。
- 边界条件：
  - 缺失 key：开发环境直接报错或至少输出明确错误，不回退为英文原文。
  - 动态文案：统一采用模板插值或函数式 formatter，禁止字符串拼接散落在组件中。
  - 搜索关键词：展示文本中文化，但保留必要英文关键词以兼容已有搜索行为。

### 6.2 接口与契约

- API/函数签名：
  - `I18nProvider`：`children` -> 提供当前 locale 与翻译字典。
  - `useI18n`：无入参 -> 返回 `t(key, params?)`。
  - `t`：`(key: TranslationKey, params?: Record<string, string | number>) -> string`。
- 错误码/异常：
  - 缺失 key 视为开发错误，直接抛异常或输出明确错误日志，不做英文兜底。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `zh-CN` 字典：按模块拆分，如 `common`、`sidebar`、`settings`、`chat`、`session`。
  - 展示型元数据从“直接字符串”迁移为“翻译 key + 搜索关键词”。
- 迁移策略：
  - 先新增字典与访问层。
  - 再迁移集中定义文件。
  - 最后按页面批量替换硬编码文案。
  - 迁移期间禁止新增新的英文硬编码。

### 6.4 兼容性与发布

- 兼容策略：内部 slug、id、route、配置键完全不变；只替换展示层文本来源。
- 发布步骤：
  - 先完成设置与导航中文化。
  - 再完成聊天/会话/各设置分区中文化。
  - 最后做一次全 UI 英文残留扫描与人工巡检。

### 6.5 可观测性

- 日志：缺失翻译 key 时打印模块、key 与调用上下文。
- 指标：暂不新增埋点，使用构建期扫描与人工验收作为主要控制手段。
- 告警：开发/测试环境出现缺 key 视为阻塞问题，不进入最终交付。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] `packages/ui` 首屏、侧边栏、设置首页、设置分组、常见设置分页面文案默认显示中文。
  - [ ] `packages/ui` 中不再新增用户可见硬编码英文；新增文案必须通过字典层接入。
  - [ ] 设置页搜索在中文展示下仍可通过常见中文词和必要英文词命中目标页面。
  - [ ] `slug`、路由、配置键、section id 保持不变，历史行为不回归。
- 非功能验收：
  - [ ] 性能：首屏不因字典加载引入可感知卡顿，默认同步加载本地字典。
  - [ ] 可靠性：缺失翻译 key 可在开发/测试阶段被明确发现。
  - [ ] 安全：不引入远程文案加载，不新增外部依赖风险。

## 8. 里程碑与任务（Milestones）

> 原则：只拆 1-3 个里程碑；每个里程碑都必须有可验证的交付物与退出标准。里程碑内再列任务，但不要过度细碎。

### M1：建立文案基础设施与集中入口

- 交付物：可用的 `I18nProvider/useI18n/zh-CN` 基础设施，以及导航/设置元数据的 key 化改造。
- 退出标准：应用可正常启动；侧边栏与设置元数据从字典取值；无新增英文硬编码入口。
- 任务：
  - [ ] 新增前端文案模块（文件/模块：`packages/ui/src/i18n/*`）验收：可以通过 `t()` 读取 `zh-CN` 文案。
  - [ ] 注入全局 Provider（文件/模块：`packages/ui/src/main.tsx`）验收：根树可消费翻译上下文。
  - [ ] 改造设置元数据（文件/模块：`packages/ui/src/lib/settings/metadata.ts`）验收：分组名、标题、描述改为从字典层获取。
  - [ ] 改造侧边栏常量（文件/模块：`packages/ui/src/constants/sidebar.ts`）验收：导航标签和描述改为从字典层获取。

### M2：完成主要页面中文化

- 交付物：设置页、聊天页、会话页及主要 section 组件完成中文化。
- 退出标准：主流程页面人工巡检不再看到英文 UI 文案。
- 任务：
  - [ ] 改造设置首页与设置分区（文件/模块：`packages/ui/src/components/views/SettingsView.tsx`、`packages/ui/src/components/sections/**`）验收：设置相关可见文案全部中文化。
  - [ ] 改造聊天与会话相关组件（文件/模块：`packages/ui/src/components/chat/**`、`packages/ui/src/components/session/**`）验收：聊天主流程可见文案全部中文化。

### M3：残留扫描、验收与扩展预留

- 交付物：英文残留清单归零或明确例外项，形成后续扩展规范。
- 退出标准：构建、lint、类型检查通过；人工验收通过；例外项已记录。
- 任务：
  - [ ] 全目录残留扫描（文件/模块：`packages/ui/src/**`）验收：用户可见英文仅保留明确批准的品牌名/协议名。
  - [ ] 建立文案接入规范（文件/模块：文档或注释约束）验收：后续新增页面知道如何接入字典层。
  - [ ] 最终验证（文件/模块：全 UI）验收：`bun run type-check`、`bun run lint`、`bun run build` 通过，人工巡检通过。

## 9. 执行计划与闭环

- 执行顺序：M1 -> M2 -> M3
- 每个里程碑验证：
  - M1：启动应用检查侧边栏与设置元数据是否已取自字典。
  - M2：逐页面人工巡检设置、聊天、会话主路径。
  - M3：执行 `bun run type-check`、`bun run lint`、`bun run build`，并结合残留扫描确认用户可见英文是否清零。
- 最终回报：变更摘要 + 验收勾选 + 风险残留 + 下一步。
