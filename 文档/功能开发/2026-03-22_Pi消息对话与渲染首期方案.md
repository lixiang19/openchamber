# Pi 消息对话与渲染首期方案

- 状态：草案
- 日期：2026-03-22
- Owner：AI / 待定
- 目标版本/里程碑：Pi Web 首期接入

## 1. 背景与问题

- 背景：OpenAurora 计划从 OpenCode 迁移到 `pi`，但当前第一优先级不是完整迁移所有能力，而是先让 Web 界面能够正常对话，并稳定渲染消息与工具结果。
- 现象/痛点：当前 Web 端发送消息、接收流式事件、写入 store、渲染消息列表，整体都强依赖 OpenCode 的 `/api/* + SSE + SDK Part` 结构；而 Pi 官方推荐的嵌入方式是 `createAgentSession()` / `AgentSession`，事件模型是 `message_update`、`tool_execution_*`、`turn_end` 等，边界并不一致。
- 成功定义：在不做 `question` / `permission` / 扩展 UI / provider-model-agent 前端接管的前提下，OpenAurora Web 能基于 Pi SDK 完成一次完整对话，并在消息列表中显示用户消息、assistant 文本流、工具调用过程、工具结果和基础子代理摘要。

## 2. 目标与非目标

- 目标：
  - 让 Web 首期只覆盖“发消息 -> Pi 执行 -> 界面流式显示消息与工具结果 -> 回合结束”。
  - 在 UI 层建立最小中立消息语义，避免消息列表继续直接绑定 OpenCode 事件名。
  - 把 Pi 作为 `packages/web/server/index.js` 内的 runtime 宿主，而不是把 Pi 伪装成 OpenCode 后端。
- 非目标：
  - 首期不做 `question` / `permission`。
  - 首期不做 `ctx.ui`、`extension_ui_request`、`setWidget`、`setStatus`、`select`、`input` 等扩展交互。
  - 首期不让 Web 接管 `provider` / `model` / `agent` 的真实决策，选择权继续留在 Pi runtime。
  - 首期不追求兼容所有 Pi 插件体验，只保证基础消息流和工具结果可见。

## 3. 现状探索（Explorer）

- 入口与调用链：
  - `packages/ui/src/lib/opencode/client.ts:607` - `sendMessage()` 是前端发消息入口，当前直接请求 `/session/:id/prompt_async`。
  - `packages/ui/src/lib/opencode/client.ts:705` - 请求体里显式传 `providerID`、`modelID`、`agent`、`variant` 和 `parts`，说明输入契约仍是 OpenCode 风格。
  - `packages/ui/src/hooks/useEventStream.ts:1115` - 前端核心按 `message.part.updated` 把 part 写入消息 store。
  - `packages/ui/src/hooks/useEventStream.ts:1283` - 前端核心按 `message.part.delta` 追加文本增量。
  - `packages/ui/src/hooks/useEventStream.ts:1803` - 当前还直接消费 `permission.asked`。
  - `packages/ui/src/hooks/useEventStream.ts:1930` - 当前还直接消费 `question.asked`。
  - `packages/ui/src/stores/types/sessionTypes.ts:137` - `SessionStore` 是消息、权限、问题、会话状态的聚合边界。
  - `packages/ui/src/stores/types/sessionTypes.ts:144` - 消息在 store 中的真实形态仍是 `Map<string, { info: Message; parts: Part[] }[]>`，底层绑定 `@opencode-ai/sdk/v2` 的 `Message` / `Part`。
  - `packages/ui/src/components/chat/message/parts/ToolPart.tsx:763` - `TaskToolSummary` 已能显示 task/subagent 摘要，说明工具消息展示层可复用。
  - `packages/web/server/index.js:6631` - 当前 `/api/event` 直接转发 OpenCode SSE。
  - `packages/web/server/index.js:6632` - 当前 `/api/global/event` 也直接转发 OpenCode SSE。
  - `packages/web/server/index.js:6760` - 大消息体仍按 OpenCode 的 session message 路由做专门转发。
- 关键数据结构/状态：
  - 前端当前最核心的状态不是“会话事件”，而是“OpenCode Message/Part 被前端拼装后写入 `SessionStore`”。
  - `permission` 与 `question` 已在 `SessionStore` 中独立建模，说明它们已经侵入主消息流；首期如果不砍掉，会继续拖住 Pi 首次接入范围。
  - `ToolPart` 已具备“工具摘要 + 输出 + 子会话跳转”的展示基础，说明首期重点不在重写消息组件，而在输入该组件的数据边界。
- 约束与坑点：
  - 当前消息列表依赖 OpenCode 的事件名和 `Part` 结构，不能直接喂 Pi 的 `message_update` / `tool_execution_*` 事件。
  - 当前 server 仍以 OpenCode 代理为中心，如果继续沿这条路做“协议翻译”，会把 Pi 的接入长期锁死在兼容层里。
  - 当前 store 直接使用 OpenCode SDK 类型，导致“渲染语义”和“后端协议”没有被切开。

## 4. 资料与依据（Librarian）

- 关键结论：
  - `docs/sdk.md` 明确说明 `createAgentSession()` 默认通过 `ResourceLoader` / `DefaultResourceLoader` 发现扩展、skills、prompts、themes 和配置，适合作为 Node/TypeScript 宿主接入入口。
  - `docs/sdk.md` 明确说明 `cwd` 与 `agentDir` 控制资源发现、settings、models、auth、sessions 等路径边界，Pi 适合作为宿主内 runtime，而不是远端 HTTP 服务。
  - `docs/json.md` 给出了 `AgentSessionEvent` / `AgentEvent` 事件层：首期真正需要的是 `message_start`、`message_update`、`message_end`、`tool_execution_start`、`tool_execution_update`、`tool_execution_end`、`turn_end`、`agent_end`。
  - `docs/json.md` 说明 `message_update` 携带 `assistantMessageEvent`，适合映射成文本增量、思考增量、工具调用增量等 UI 语义。
  - `docs/extensions.md` 说明 `ctx.ui`、`ctx.ui.custom()`、`registerMessageRenderer()` 等能力是扩展/TUI 交互层，不应进入 Web 首期范围。
  - `docs/sdk.md` 说明 `SettingsManager` 可用文件态或内存态；这意味着 OpenAurora 可显式控制 Pi 运行时配置读取方式，但首期不需要把这些配置暴露给前端。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：首期直接在 `packages/web/server/index.js` 内嵌 Pi SDK，会话侧产出 Pi 原生事件；Web 端新增最小中立消息模型与 Pi 专用事件摄取链路，消息列表继续复用现有渲染组件，但不再直接消费 OpenCode 事件名。
- 取舍：这样做会多一次前端消息层整理，但它是根治性改法；不再把 Pi 接入建立在“翻译成 OpenCode 协议”的前提上，也不会为了首期目标去承接 `question` / `permission` / 扩展 UI 这些高复杂度能力。
- 影响面：主要影响 `packages/web/server/index.js` 的会话宿主职责、前端消息摄取层与 store 类型；`MessageList`、`ToolPart` 等视图组件应尽量少动。

### 5.2 风险与回滚

- 风险：
  - 前端当前直接依赖 OpenCode `Message/Part`：缓解措施是先引入 UI 自己的最小消息模型，再在摄取层做单向转换。
  - Pi 事件流和现有 SSE 使用习惯不同：缓解措施是 server 明确只暴露“会话消息事件流”，不要再背 OpenCode 的全量 API 包袱。
  - `question` / `permission` 暂时不接后，某些 prompt 可能暴露出待处理交互：缓解措施是首期明确禁用这些场景，先用纯消息与工具链路验收。
- 回滚：
  - 保留当前 OpenCode 路径，通过运行时开关切回原 `OpenCode SSE + client`。
  - Pi 首期链路独立在新命名空间下实现，不覆盖现有 OpenCode 路由与 store 行为；失败时可直接断开 Pi 入口。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：
  - 用户在 Web 输入框发送文本。
  - 前端调用新的 Pi 会话发送入口，而不是继续走 OpenCode 的 `prompt_async`。
  - Web server 使用 `createAgentSession()` / `AgentSession` 驱动一次 Pi 会话执行。
  - server 订阅 Pi 事件，并把它们整理为 Web 首期需要的消息事件流。
  - 前端把这些事件写入中立消息 store，消息列表和 `ToolPart` 直接消费中立后的渲染数据。
- 边界条件：
  - 只支持文本输入与既有文件输入，不支持结构化问答与权限确认。
  - 若收到 Pi 的 custom message，首期允许降级为普通消息块或工具附加信息，但不能丢失文本与工具结果。
  - 若扩展触发 `extension_ui_request`，首期直接标记为未支持，不做伪交互。

### 6.2 接口与契约

- API/函数签名：
  - `POST /api/pi/session/:id/prompt`：`{ text, files? } -> { accepted: true, clientMessageId }`
  - `GET /api/pi/event?sessionId=...`：返回 Pi 首期消息事件流，事件类型只保留 UI 需要的稳定语义。
  - 前端内部新增：`PiConversationEvent -> RenderableMessage/RenderablePart` 的归并器。
- 错误码/异常：
  - Pi 会话创建失败：返回 `503 runtime_unavailable`，前端明确提示，不做兜底重试。
  - 收到未支持事件：server 记录日志并下发 `unsupported_event` 调试事件；前端不让消息流崩掉。
  - 发送过程中用户中断：显式下发 `session_abort`，同步收敛流式状态。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `RenderableConversationMessage`
    - `id: string`
    - `sessionId: string`
    - `role: 'user' | 'assistant' | 'system'`
    - `parts: RenderablePart[]`
    - `status: 'streaming' | 'completed' | 'error'`
    - `createdAt: number`
  - `RenderablePart`
    - `id: string`
    - `kind: 'text' | 'reasoning' | 'tool' | 'custom'`
    - `text?: string`
    - `toolName?: string`
    - `toolCallId?: string`
    - `toolState?: 'pending' | 'running' | 'completed' | 'error'`
    - `input?: Record<string, unknown>`
    - `output?: string`
    - `metadata?: Record<string, unknown>`
  - `ConversationStreamState`
    - `sessionId: string`
    - `messageId: string`
    - `phase: 'idle' | 'streaming' | 'cooldown'`
    - `lastEventAt: number`
- 迁移策略：
  - 首期新增 UI 自有消息模型，不继续向该模型灌 OpenCode SDK 的原始 `Part`。
  - 现有 `SessionStore.messages` 可以先并存一层投影结果，待 Pi 路径稳定后再决定是否整体替换旧的 `Message/Part` 依赖。

### 6.4 兼容性与发布

- 兼容策略：首期采用 Pi 独立入口，不在语义层伪装成 OpenCode；同一版本允许 OpenCode 与 Pi 两条链路并存，但不共享协议假设。
- 发布步骤：
  - 先发布 Pi 文本对话与工具结果渲染。
  - 再根据效果决定是否继续接 `custom message` 专门渲染。
  - 最后才考虑 `question` / `permission` / 扩展 UI。

### 6.5 可观测性

- 日志：
  - 记录 Pi session 创建、prompt 提交、关键事件流转、未知事件、消息归并失败。
- 指标：
  - 首 token 时间、整轮完成时间、工具调用次数、消息归并失败次数、未知事件次数。
- 告警：
  - 连续出现未知事件或消息归并异常时，提示当前 UI 语义与 Pi 事件模型发生漂移。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] Web 可以向 Pi 发起一次文本对话，并稳定收到 assistant 文本流。
  - [ ] Web 可以显示 Pi 的工具调用开始、进行中、结束状态，以及最终工具结果。
  - [ ] `ToolPart` 能继续显示基础 task/subagent 摘要，不要求完整复刻 Pi TUI。
  - [ ] 首期流程中不再依赖 `question.asked` / `permission.asked` 才能完成基本对话。
- 非功能验收：
  - [ ] 性能：单轮文本流式渲染无明显卡顿，前端消息归并不出现指数级重算。
  - [ ] 可靠性：未知 Pi 事件不会导致消息列表崩溃，至少可以降级日志化。
  - [ ] 安全：Web 首期不新增扩展 UI 执行面，不把 Pi 侧权限决策错误地下沉到浏览器。

## 8. 里程碑与任务（Milestones）

> 原则：只拆 1-3 个里程碑；每个里程碑都必须有可验证的交付物与退出标准。里程碑内再列任务，但不要过度细碎。

### M1：切出前端中立消息层

- 交付物：前端具备一层不依赖 OpenCode 事件名的消息归并模型与渲染输入。
- 退出标准：消息列表和 `ToolPart` 可以只消费中立消息数据，旧的 OpenCode 事件细节不再直接泄漏到渲染层。
- 任务：
  - [ ] 新增会话渲染模型与归并器（文件/模块：`packages/ui/src/lib/conversation/*`）验收：可表达文本、工具、custom 占位三类 part。
  - [ ] 调整 store 投影边界（文件/模块：`packages/ui/src/stores/useSessionStore.ts`、`packages/ui/src/stores/types/sessionTypes.ts`）验收：消息列表能从中立模型读取数据。
  - [ ] 收窄 `MessageList` / `ToolPart` 对 OpenCode 原始 `Part` 的依赖（文件/模块：`packages/ui/src/components/chat/message/parts/ToolPart.tsx`）验收：现有展示不因底层换源而崩。

### M2：接入 Pi SDK 会话链路

- 交付物：Web server 内可创建 Pi 会话、提交 prompt、订阅事件，并向前端发送首期消息事件流。
- 退出标准：一次真实 prompt 可以完成“发送 -> 文本流 -> 工具状态 -> 回合结束”的闭环。
- 任务：
  - [ ] 在 server 侧新增 Pi runtime 宿主（文件/模块：`packages/web/server/lib/pi/*` 或 `packages/web/server/index.js`）验收：能创建/持有 `AgentSession`。
  - [ ] 新增 Pi prompt 与事件路由（文件/模块：`packages/web/server/index.js`）验收：前端可订阅 Pi 会话事件流。
  - [ ] 实现 Pi 事件到前端中立事件的整理（文件/模块：server Pi adapter）验收：覆盖 `message_update`、`tool_execution_*`、`turn_end`、`agent_end`。

### M3：端到端联调与收敛

- 交付物：Pi 首期 Web 对话链路稳定，OpenCode 与 Pi 可以通过开关切换。
- 退出标准：至少完成文本对话、`read`/`bash` 工具调用、基础 subagent 摘要显示三类演练。
- 任务：
  - [ ] 联调前端发送入口（文件/模块：`packages/ui/src/lib/opencode/client.ts` 或新增 Pi client）验收：Pi 会话不再依赖 `prompt_async`。
  - [ ] 补齐流状态与中断收敛（文件/模块：`packages/ui/src/hooks/useEventStream.ts` 或新增 Pi event hook）验收：刷新、取消、回合结束状态一致。
  - [ ] 增加最小验证脚本/手工验证步骤（文件/模块：文档与 server 日志）验收：能复现三条首期验收路径。

## 9. 执行计划与闭环

- 执行顺序：M1 -> M2 -> M3
- 每个里程碑验证：
  - M1：用本地假事件或现有 OpenCode 数据投影验证中立消息模型可以驱动消息列表。
  - M2：启动 Pi SDK 会话，验证 `message_update`、`tool_execution_start`、`tool_execution_end`、`turn_end` 能完整流到前端。
  - M3：进行 3 组真实演练：纯文本对话、`read`/`bash` 工具回合、带基础 subagent 摘要的回合。
- 最终回报：变更摘要 + 验收勾选 + 风险残留 + 下一步。
