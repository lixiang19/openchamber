# Agent级细粒度编辑权限配置 方案

- 状态：草案
- 日期：2026-03-26
- Owner：Codex / OpenChamber
- 目标版本/里程碑：Pi 原生 agent 权限首期

## 1. 背景与问题

- 背景：项目已经切到 Pi SDK 主线，但 agent 权限仍停留在粗粒度工具开关，无法表达“禁用编辑”或“只允许编辑 Markdown”这类真实约束。
- 现象/痛点：当前 `permission` 只能做 `allow|deny` 的工具级配置，运行时只会把被 `deny` 的工具从可用工具集里移除，无法基于路径、后缀或目录做强约束。
- 现象/痛点：前端 agent 设置页当前也是“勾掉某些工具”的模型，保存时只会写出 `{ tool: 'deny' }` 这种对象，根本没有文件选择范围的表达能力。
- 现象/痛点：如果只在 UI 上做“看起来像禁用编辑”的开关，而运行时没有真正拦截 `edit` / `write`，或者仍然允许 `bash` 写文件，就会形成假安全。
- 现象/痛点：用户已经明确希望配置格式尽量参考 OpenCode 权限文档，因此方案不能再发明一套完全陌生的新语法。
- 成功定义：agent frontmatter 与 agent 设置页都能声明编辑策略；运行时在 Pi SDK 模式下硬性阻断不符合策略的 `edit` / `write`；“禁用编辑”和“仅允许 `*.md`”都能稳定生效，同时配置写法接近 OpenCode 的 `permission` 规则语法。

## 2. 目标与非目标

- 目标：
  - 支持 agent 级编辑权限策略，配置格式参考 OpenCode `permission` 语法。
  - 支持两种首期核心能力：完全禁用编辑、仅允许编辑 Markdown。
  - 在 Pi SDK 运行时做真实拦截，而不是依赖前端提示或兼容层兜底。
  - 统一 primary agent 与 subagent 的权限语义，避免一边生效、一边漏掉。
  - 在 agent 配置 UI 中提供可编辑、可校验、可预览的权限配置入口。
- 非目标：
  - 不做全局 / 项目 / agent 三层权限体系；本轮只做 agent 级。
  - 不引入 OpenCode 运行时，也不做 OpenCode 协议兼容；只参考其配置格式。
  - 不在本轮实现完整的 `ask` 审批产品闭环；首期先把 `allow` / `deny` 的静态策略做实。
  - 不做自定义扩展工具的通用写盘分类；首期只覆盖 Pi 内置 `edit` / `write`，并把它们统一归入 `edit` 权限键。
  - 不在本轮扩展 bash 细粒度写盘策略；如果要保证严格编辑边界，bash 必须显式 `deny`。

## 3. 现状探索（Explorer）

- 入口与调用链：

  - `packages/ui/src/components/sections/agents/AgentsSidebar.tsx:27` - `rulesetToPermissionConfig()` 复制 / 重命名 agent 时也只保留 `deny` 规则。
- 关键数据结构/状态：
  - `packages/ui/src/lib/runtime/types.ts:1` - 当前 `PermissionConfig` 仍是 `Record<string, PermissionAction>`，前端类型本身就不支持结构化规则。

- 约束与坑点：
  - 当前前后端都默认 `permission` 是二元对象模型，任何更细粒度配置都会同时冲击解析、运行时和 UI。
  - 现有前端还有 session 级 `permission.asked` 卡片，这和 agent frontmatter 的静态权限不是一回事，不能混为一谈。
  - 如果 `bash` 仍允许写文件，单独限制 `edit` / `write` 不能形成真正的编辑边界。

## 4. 资料与依据（Librarian）

- 关键结论：
  - OpenCode 权限文档允许把某个权限键写成简单值，或写成按模式匹配的对象规则，并采用“最后匹配优先”的规则顺序，见 `https://opencode.ai/docs/zh-cn/permissions/`。
  - OpenCode 文档里 `edit` 可以写成对象规则，例如先 `"*": "deny"` 再对白名单路径 `"allow"`，这正好能自然表达“只能编辑 md”。
  - `@mariozechner/pi-coding-agent` 官方 README 明确说明 Pi 没有内建 permission popup，推荐通过扩展自己实现安全门，见 `/Users/lixiang/.local/lib/node_modules/@mariozechner/pi-coding-agent/README.md:428`。
  - Pi 扩展 API 支持 `pi.getActiveTools()` / `pi.setActiveTools()`，可以先收缩可用工具面，见 `pi的相关资料/pi-extensions-dev/references/api.md:88`。
  - Pi 扩展事件支持 `tool_call`，并且可直接 `return { block: true, reason }` 阻断工具调用，见 `pi的相关资料/pi-extensions-dev/references/events.md:183`。
  - Pi 的官方示例已经给出“权限门”和“路径保护”的模式，说明路径级拦截应落在 `tool_call` 层，而不是 UI 提示层，见 `pi的相关资料/pi-extensions-dev/references/examples.md:136` 与 `pi的相关资料/pi-extensions-dev/references/examples.md:151`。
  - RPC 文档强调 `ctx.hasUI` 不是安全边界，`custom()` 不能作为权限门依赖；我们的方案必须在 SDK 运行时直接拦截，不依赖 RPC 特性，见 `pi的相关资料/pi-extensions-dev/guides/05-rpc-mode.md:74`。

## 5. 方案概览（主方案）

### 5.1 方案摘要

- 一句话：把 agent 的 `permission` 重构为参考 OpenCode 的声明式规则格式，允许 `edit` 既可以是简单值，也可以是模式对象；再在 Pi SDK 宿主层引入统一的权限编译器与 `tool_call` 拦截扩展，真正实现 agent 级编辑边界。
- 取舍：不继续把“编辑权限”硬塞进自定义的 `mode + paths` 包装结构，而是直接采用用户更熟悉的规则写法；代价是需要把当前旧的 `{ tool: 'deny' }` 模型一次性替换掉。
- 影响面：会改 agent frontmatter 解析、Pi session 启动逻辑、subagent 权限注入、agent 设置页 UI、前端 permission 类型与部分编辑模式推导逻辑。

主配置形态如下：

```yaml
permission:
  bash: deny
  edit:
    "*": deny
    "**/*.md": allow
    "**/*.mdx": allow
```

首期支持的两类写法：

```yaml
permission:
  bash: deny
  edit: deny
```

```yaml
permission:
  bash: deny
  edit:
    "*": deny
    "**/*.md": allow
```

语义约定：

- `permission.edit` 是逻辑权限键，不直接等于某一个 Pi 工具；它统一覆盖所有文件修改类内置工具。首期实际拦截 `edit` 与 `write`。
- `permission.edit: deny` 表示禁止所有文件修改。
- `permission.edit: allow` 表示允许所有工作区内文件修改。
- `permission.edit: { pattern: action }` 表示按路径模式匹配文件；采用“最后匹配优先”。
- `permission.bash` 仍使用简单值写法；当 `permission.edit` 不是全局 `allow` 时，`permission.bash` 必须为 `deny`，否则配置无效。
- 首期动作集合只真正落地 `allow` 与 `deny`；格式会为以后扩展 `ask` 预留，但本方案验收不包含 `ask`。

模式匹配约定：

- 参考 OpenCode 文档，用简单通配符语义：`*` 匹配零个或多个任意字符，`?` 匹配单个字符。
- 匹配对象是相对 `cwd` 归一化后的 POSIX 路径。
- 首期推荐用户使用如下常见模式：`"*"`、`"**/*.md"`、`"docs/*.md"`。

### 5.2 风险与回滚

- 风险：
  - 旧 agent 文件仍然使用对象型 `permission`：缓解措施是首期一次性迁移，不保留双 schema。
  - 只在主会话做权限门、漏掉 subagent：缓解措施是抽出共享的 `permission compiler + gate`，primary / subagent 共用。
  - 路径归一化不一致导致误判：缓解措施是统一在服务端做 `cwd` 相对路径归一化，禁止 `..`、禁止工作区外路径。
  - 前端还把编辑模式理解为 `edit` 一个 tool：缓解措施是同步改 `PermissionConfig` 类型和默认模式推导逻辑，改成读新的规则结构。
- 回滚：
  - 回滚点不是“继续兼容旧 schema”，而是把本次 schema 重构所在提交整体回退。
  - 在正式实施前，先保留本方案文档与迁移清单；如果实施中断，仓库回到旧的对象权限模型，不保留半迁移状态。

## 6. 详细设计（Spec）

### 6.1 交互/行为（如适用）

- 用户流程：
  1. 用户在 agent 设置页打开某个 agent。
  2. 在“编辑权限”区域选择两类快捷配置：`禁用编辑` 或 `仅允许 Markdown`。
  3. 高级模式下允许直接编辑规则列表，底层仍保存为 OpenCode 风格的 `pattern -> action` 对象。
  4. 若当前 `bash` 不是 `deny`，保存时直接报配置错误，不允许落盘。
  5. agent 启动时先编译权限策略，再决定 active tools，并绑定 `tool_call` 权限门。
  6. 当模型尝试编辑非授权文件时，工具调用直接失败，消息流中显示阻断原因，而不是弹出 permission 卡片。
- 边界条件：
  - `permission.edit` 为对象时，必须至少包含一条有效规则。
  - `permission.edit` 的对象规则中若没有兜底 `"*"`，系统会视为非法配置；因为首期不接受隐式默认值。
  - pattern 为空字符串、绝对路径、包含 `..` 的越界路径规则：禁止保存。
  - 目标路径不在 `cwd` 下：直接阻断。
  - `permission` 中出现首期未支持的细粒度对象键时，加载时报错而不是悄悄忽略。

### 6.2 接口与契约

- API/函数签名：

```ts
type PermissionAction = "allow" | "deny";
type PermissionRuleObject = Record<string, PermissionAction>;
type PermissionRuleValue = PermissionAction | PermissionRuleObject;

type AgentPermissionKey =
  | "read"
  | "grep"
  | "find"
  | "ls"
  | "bash"
  | "edit"
  | "question"
  | "subagent";

interface AgentPermissionConfig {
  [key: AgentPermissionKey]?: PermissionRuleValue;
}

interface CompiledPermissionRule {
  pattern: string;
  action: PermissionAction;
}

interface ResolvedAgentPermissionPolicy {
  raw: AgentPermissionConfig;
  activeToolNames: string[];
  editRules: CompiledPermissionRule[];
  bashAction: PermissionAction;
}

function normalizeAgentPermission(input: unknown): AgentPermissionConfig;
function compileAgentPermission(cwd: string, input: AgentPermissionConfig | undefined): ResolvedAgentPermissionPolicy;
function matchPermissionRule(path: string, rules: CompiledPermissionRule[]): PermissionAction;
function createPermissionGateExtension(policy: ResolvedAgentPermissionPolicy): ExtensionFactory;
function extractMutationPath(toolName: string, input: unknown): string | null;
```

- 契约规则：
  - `normalizeAgentPermission()` 是唯一 schema 入口，`agents.js`、`sdk-host.js`、`subagent.js` 都只能消费归一化结果。
  - `compileAgentPermission()` 负责校验、规则归一化、active tools 计算，禁止各调用方重复拼接规则。
  - `edit` 是逻辑权限键，服务端要把 Pi 的 `edit` / `write` 工具都映射到它。
  - `extractMutationPath()` 首期只支持 Pi 内置 `edit` / `write`，分别读取 `input.path`。
  - `createPermissionGateExtension()` 在 `tool_call` 上强制执行编辑边界；任何不匹配都返回 `{ block: true, reason }`。
- 错误码/异常：
  - `INVALID_AGENT_PERMISSION_SCHEMA`：frontmatter 结构不合法。
  - `INVALID_EDIT_RULESET`：`permission.edit` 对象规则非法。
  - `MISSING_EDIT_FALLBACK_RULE`：`permission.edit` 是对象但缺少 `"*"` 规则。
  - `EDIT_POLICY_REQUIRES_BASH_DENY`：严格编辑策略下 bash 未禁用。
  - `EDIT_TARGET_OUTSIDE_WORKSPACE`：目标路径不在当前工作区内。
  - `EDIT_TARGET_NOT_ALLOWED`：目标路径不匹配允许规则。

### 6.2.1 如何让 Pi 真正遵守这套复杂配置

- 核心原则：Pi SDK 不会原生理解这套 OpenCode 风格 `permission` 规则；必须由 OpenChamber 的宿主层先把配置编译成运行时策略，再把策略注入 session。
- 执行链：

```text
agent.md frontmatter
  -> packages/web/server/lib/pi/agents.js::normalizeAgentPermission()
  -> packages/web/server/lib/pi/sdk-host.js::compileAgentPermission()
  -> 生成 ResolvedAgentPermissionPolicy
  -> A. 根据策略收缩 active tools
  -> B. 通过 extensionFactories 注入 permission gate
  -> createAgentSession(...)
  -> session.bindExtensions(...)
  -> tool_call 时检查 path / toolName
  -> 允许则继续执行，拒绝则 block
```

- A. 收缩工具面：
  - `compileAgentPermission()` 先根据策略计算 `activeToolNames`。
  - 当 `permission.edit = deny` 时，直接从主会话可用工具中移除 `edit`、`write`。
  - 这一步在 primary session 上通过 `session.setActiveToolsByName(activeToolNames)` 落地，对应当前 `packages/web/server/lib/pi/sdk-host.js:471` 的接入点。
  - 这一步在 subagent 上通过 `createAgentSession({ tools })` 落地，对应当前 `packages/web/server/lib/pi/extensions/subagent.js:486` 之后的 session 创建链路。
- B. 注入权限门扩展：
  - 仅靠 active tools 不够，因为 `permission.edit` 是对象规则时，`edit` / `write` 仍需保留在工具集中，等调用时再决定目标路径是否允许。
  - 因此要用 `DefaultResourceLoader({ extensionFactories: [...] })` 给每个 session 注入一个内联扩展工厂。Pi 官方 SDK 已支持这种做法，见 `/Users/lixiang/.local/lib/node_modules/@mariozechner/pi-coding-agent/docs/sdk.md:520`。
  - 该扩展在 `pi.on("tool_call")` 中读取工具输入。Pi 官方事件文档已经确认 `tool_call` 可拦截并返回 `{ block: true, reason }`，见 `pi的相关资料/pi-extensions-dev/references/events.md:183`。
- 权限门内部逻辑：

```ts
pi.on("tool_call", async (event) => {
  const targetPath = extractMutationPath(event.toolName, event.input);
  if (!targetPath) return;

  const logicalPermission = mapToolToPermission(event.toolName);
  if (logicalPermission !== "edit") return;

  const normalizedPath = normalizePathRelativeToCwd(ctx.cwd, targetPath);
  if (!normalizedPath) {
    return { block: true, reason: "EDIT_TARGET_OUTSIDE_WORKSPACE" };
  }

  const action = matchPermissionRule(normalizedPath, policy.editRules);
  if (action !== "allow") {
    return { block: true, reason: `Editing ${normalizedPath} is not allowed for this agent.` };
  }
});
```

- 逻辑权限映射：
  - `permission.edit` 不是 Pi 的原生工具名，而是我们定义的逻辑权限键。
  - 在运行时要显式映射：`edit` 工具 -> `edit` 权限键，`write` 工具 -> `edit` 权限键。
  - 这样用户写一条 `permission.edit`，就能同时控制两类文件修改能力，而不需要再分别写 `edit` / `write`。
- Primary session 接入方式：
  - 当前 `packages/web/server/lib/pi/sdk-host.js:697` 已经创建了 `DefaultResourceLoader`，这里只需把 `extensionFactories` 扩展为：追加 `createPermissionGateExtension(policy)`。
  - 当前 `packages/web/server/lib/pi/sdk-host.js:711` 已经调用 `createAgentSession()`；session 创建后继续沿用现有 `bindExtensions()` 流程，不需要改成 RPC。
- Subagent 接入方式：
  - 当前 `packages/web/server/lib/pi/extensions/subagent.js:480` 已经为子代理创建 `DefaultResourceLoader`。
  - 这里同样注入 `createPermissionGateExtension(policy)`，并在 `createAgentSession()` 时使用编译后的 `tools`。
  - 这样主 agent 与 subagent 共用同一套规则编译和阻断逻辑，不会出现父子会话行为不同。
- 为什么不能只靠前端或提示词：
  - 前端 UI 只负责配置与展示，不能成为安全边界。
  - 提示词只能“建议模型遵守”，不能阻止真实的工具调用。
  - 真正让 Pi 听这套复杂配置的唯一方法，是在宿主层把配置转成 `active tools + tool_call gate` 两层机制。

### 6.2.2 `tool_call gate` 设计

- 设计目标：
  - gate 只做一件事：在工具真正执行前，根据已经编译好的权限策略做纯判定。
  - gate 不解析 frontmatter、不保存配置、不弹 UI、不做兼容；它只消费 `ResolvedAgentPermissionPolicy`。
  - gate 必须同时服务 primary session 和 subagent session，禁止两边维护两套权限判断逻辑。
- 模块拆分：
  - `packages/web/server/lib/pi/permissions/normalize.js`：解析 frontmatter 的 `permission`。
  - `packages/web/server/lib/pi/permissions/compile.js`：把声明式配置编译成运行时策略。
  - `packages/web/server/lib/pi/permissions/match.js`：做路径归一化、通配符匹配、最后匹配优先求值。
  - `packages/web/server/lib/pi/extensions/permission-gate.js`：提供 `createPermissionGateExtension(policy)`，只负责 `tool_call` 拦截。
- gate 输入结构：

```ts
type PermissionAction = "allow" | "deny";

type CompiledPermissionRule = {
  pattern: string;
  action: PermissionAction;
};

interface ResolvedAgentPermissionPolicy {
  agentName: string;
  cwd: string;
  toolActions: Partial<Record<"bash" | "read" | "grep" | "find" | "ls" | "question" | "subagent", PermissionAction>>;
  editRules: CompiledPermissionRule[] | null;
  activeToolNames: string[];
}
```

- 运行时判定流程：

```text
tool_call event
  -> mapToolToLogicalPermission(toolName)
  -> extractMutationPath(toolName, input)
  -> normalizePathRelativeToCwd(policy.cwd, path)
  -> matchPermissionRule(normalizedPath, policy.editRules)
  -> allow => 继续执行
  -> deny => return { block: true, reason }
```

- 逻辑权限映射：
  - `permission.edit` 是逻辑权限键，不等于某个 Pi 原生工具名。
  - 首期运行时固定映射：`edit` 工具 -> `edit` 权限、`write` 工具 -> `edit` 权限。
  - 用户写一条 `permission.edit` 即可统一控制全部文件修改能力，不再分别配置 `edit` / `write`。
- 路径提取：
  - 首期只支持 Pi 内置 `edit` / `write`；两者都从 `event.input.path` 读取目标文件。
  - 如果工具缺少目标路径，直接阻断，错误码为 `EDIT_TARGET_PATH_MISSING`。
- 路径归一化：
  - 输入路径必须先基于 `policy.cwd` 做 `path.resolve()`。
  - 再通过 `path.relative(policy.cwd, absoluteTarget)` 生成相对工作区路径。
  - 最终统一转为 POSIX 风格 `/` 分隔，用于规则匹配。
  - 任何结果为绝对路径、空路径、`..` 或 `../` 开头的路径，都视为工作区外，直接返回 `EDIT_TARGET_OUTSIDE_WORKSPACE`。
- 规则匹配：
  - 参考 OpenCode 文档，采用简单通配符语义：`*` 匹配零个或多个字符，`?` 匹配一个字符。
  - 匹配顺序采用“最后匹配优先”。
  - 首期默认值不是隐式 allow；如果 `permission.edit` 是对象规则，就必须显式提供 `"*"`。
- gate 伪代码：

```ts
export function createPermissionGateExtension(policy: ResolvedAgentPermissionPolicy) {
  return (pi: ExtensionAPI) => {
    pi.on("tool_call", async (event) => {
      const logicalPermission = mapToolToLogicalPermission(event.toolName);
      if (logicalPermission !== "edit") {
        return;
      }

      const targetPath = extractMutationPath(event.toolName, event.input);
      if (!targetPath) {
        return { block: true, reason: "EDIT_TARGET_PATH_MISSING" };
      }

      const normalizedPath = normalizePathRelativeToCwd(policy.cwd, targetPath);
      if (!normalizedPath) {
        return { block: true, reason: "EDIT_TARGET_OUTSIDE_WORKSPACE" };
      }

      const action = matchPermissionRule(normalizedPath, policy.editRules || []);
      if (action !== "allow") {
        return {
          block: true,
          reason: `EDIT_TARGET_NOT_ALLOWED:${normalizedPath}`,
        };
      }
    });
  };
}
```

- 与 `active tools` 的关系：
  - `permission.edit = deny` 时，优先在 session 创建阶段移除 `edit` / `write`，这是第一层粗粒度防线。
  - `permission.edit` 为对象规则时，`edit` / `write` 仍需保留在 active tools 中，由 gate 在调用瞬间决定是否允许。
  - 因此两层必须并存：`active tools` 负责裁剪能力面，`tool_call gate` 负责路径级强约束。
- primary session 接入：
  - 在 `packages/web/server/lib/pi/sdk-host.js` 的 `DefaultResourceLoader({ ... })` 中追加 `extensionFactories: [createPermissionGateExtension(policy)]`。
  - 在 `createAgentSession()` 完成后继续沿用现有 `session.bindExtensions()`，不改 RPC，不新增桥接协议。
  - agent 切换时先重新编译 policy，再更新 active tools 和 gate 所绑定的 session。
- subagent 接入：
  - 在 `packages/web/server/lib/pi/extensions/subagent.js` 创建 `DefaultResourceLoader` 时，同样追加 `createPermissionGateExtension(policy)`。
  - subagent 的 `tools` 参数与 permission gate 都来自同一个 `compileAgentPermission()` 结果。
  - 这样父会话与子会话共享同一套编辑权限语义，不会出现“父会话挡住了，子会话没挡住”的漏洞。
- 为什么首期要求 `bash: deny`：
  - 只拦 `edit` / `write` 无法阻止 `bash` 通过重定向、脚本、`sed -i`、`python -c` 等方式改文件。
  - 所以只要 `permission.edit` 不是全局 `allow`，就必须强制 `permission.bash = deny`，否则整个编辑权限边界不成立。
- 错误输出与可观测性：
  - gate 不直接生成长文案，而是统一返回结构化 reason 前缀，例如：`EDIT_TARGET_PATH_MISSING`、`EDIT_TARGET_OUTSIDE_WORKSPACE`、`EDIT_TARGET_NOT_ALLOWED:<path>`。
  - 上层消息展示与日志系统再把这些 reason 转成用户可见文本。
- 最小测试矩阵：
  - `permission.edit = deny`：`edit foo.md`、`write foo.md` 都被阻断。
  - `permission.edit = allow`：`edit foo.ts`、`write foo.md` 都放行。
  - `permission.edit = { "*": "deny", "**/*.md": "allow" }`：`docs/a.md` 放行，`src/a.ts` 阻断。
  - 工作区外路径：`../a.md`、`/tmp/a.md` 一律阻断。
  - 规则顺序：后写的规则覆盖前面的规则，验证“最后匹配优先”。

### 6.3 数据与存储（如适用）

- Schema/字段：
  - `permission.bash`：shell 命令权限，首期只接受简单值。
  - `permission.edit`：编辑权限，可为简单值，也可为规则对象。
  - 其他权限键首期保持简单值，不开放对象规则编辑 UI。
- 迁移策略：
  - 不做兼容解析。
  - 现有对象型配置（例如 `permission: { edit: deny, write: deny }`）在实施时一次性改写为新结构。
  - 迁移规则：

```yaml
permission:
  edit: deny
  write: deny
```

  改为：

```yaml
permission:
  edit: deny
```

  或：

```yaml
permission:
  bash: deny
  edit:
    "*": deny
    "**/*.md": allow
```

  - 前端 `PermissionConfig` 类型同步从 `Record<string, PermissionAction>` 改成 `PermissionAction | Record<string, PermissionAction>` 的结构化模型，避免 UI 层再把新 schema 压扁回旧模型。

### 6.4 兼容性与发布

- 兼容策略：参考 OpenCode 的语法，不兼容旧 `permission` 对象；新旧 schema 不并存。
- 发布步骤：
  1. 先落服务端 schema 与校验。
  2. 再接入 shared permission compiler 与 runtime gate。
  3. 再改前端 agent 设置页与类型。
  4. 最后迁移仓库内 / 内置 agent 定义。

### 6.5 可观测性

- 日志：
  - agent 加载时打印归一化后的权限摘要。
  - 配置非法时记录 agent 名称、来源文件、错误码。
  - 运行时阻断编辑时记录 `agent`、`toolName`、`path`、`reason`。
- 指标：
  - `agent_permission_invalid_total`
  - `agent_edit_block_total`
  - `agent_edit_allowed_total`
- 告警：
  - 某 agent 连续出现大量 `agent_permission_invalid_total` 时，说明配置迁移失败。
  - `agent_edit_block_total` 异常飙升时，说明模型提示词或权限配置不匹配。

## 7. 验收标准（必须可验证）

- 功能验收：
  - [ ] agent frontmatter 能正确表达 `permission.edit = deny`。
  - [ ] agent frontmatter 能正确表达 `permission.edit = { "*": "deny", "**/*.md": "allow" }`。
  - [ ] primary agent 与 subagent 都会在运行时阻断不符合规则的 `edit` / `write`。
  - [ ] 配置页能编辑“禁用编辑”和“仅允许 Markdown”，并在保存前完成校验。
  - [ ] 当 `permission.edit` 不是全局 `allow` 且 `permission.bash != deny` 时，配置保存失败并给出明确原因。
- 非功能验收：
  - [ ] 性能：权限编译和单次路径匹配不会明显拉长首个 tool call，额外开销保持在毫秒级。
  - [ ] 可靠性：同一份 agent 配置在主会话与 subagent 上得到一致结果。
  - [ ] 安全：不依赖前端 UI 或 RPC 交互兜底，运行时直接阻断越权编辑。
