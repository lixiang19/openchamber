结论先说：这批 bug 的主因不是某一个组件写坏了，而是 **Pi 流式事件进入前端后，被重复投影了太多次，而且流式时序又被 RAF 和虚拟列表测量拆开了**。性能卡顿、重复显示、局部不显示，基本都能从这两点推出。

优先级排序我会这样排：

P0：先修重复与不显示
P1：再修流式卡顿
P2：最后做架构收口

具体是：

1. 先消掉 `toolResult` 重复路径
2. 先把“流式尾巴”从虚拟列表里拆出去
3. 去掉全量 RAF 投影，改成按 session 增量更新
4. 去掉深度消息重用检查，改成 revision/signature
5. 再逐步废弃 `ChatMessageEntry` 热路径

第 1 点，多层数据转换架构的问题。

现在的链路实际上是：

`Pi SSE -> reducer(state.sessions) -> useEventStream projectPiStateToStores -> MessageList(baseDisplayMessages/displayMessages) -> useTurnRecords/projectTurnRecords -> RenderEntry -> UI`

其中 reducer 每次流式增量都会复制 `messages` 数组、复制 assistant `content` blocks；`useEventStream` 又把整个 `PiClientState` 投影到多个 store；`MessageList` 再继续做一轮消息归一化、overlay、turn 投影、entry 投影。也就是说，一个 token 不是“改一个块”，而是“经过多层全量重建后再渲染”。

更关键的是，这里不是单纯 DTO 传递。`ChatMessageEntry` 这层已经在做“语义加工”：过滤 synthetic parts、把 shell bridge 重写、把 tool result 塞回 assistant tool part、再把多条 assistant message collapse 成一条 merged message。它已经不是薄中间层，而是第二套消息模型。中间层一旦承担这种语义职责，就很容易引入“重复、错配、隐藏”。

这里最明显的重复 bug 候选是：reducer 在 tool end / turn end 时会把 `toolResult` 追加成独立消息；但 `buildMinimalMessageEntryFromPi` 又会按 `toolCallId` 把同一个 tool result 合并进 assistant 的 tool part 输出里；而 `projectTurnRecords` 只分组 user/assistant，`toolResult` 仍会作为 ungrouped message 留在列表中。于是同一份工具结果很可能既出现在 assistant 工具块里，又单独出现在消息流里。这个路径非常像你说的“重复显示”。

还有一个“错配”风险：当 Pi 的 `toolCall` block 没有 id 时，`buildMinimalMessageEntryFromPi` 会 fallback 按 tool name 去匹配 execution。相同工具连续调用时，这个策略天然有歧义，容易把 A 调用的执行结果挂到 B 调用上。

第 2 点，`useMemo` 是否过度。

是，整体上偏过度了，但不是所有 `useMemo` 都该删。问题在于：上游对象身份并不稳定，下游 memo 又分得太碎，导致缓存命中率低，反而增加比较、维护和依赖传播成本。`TurnBlock` 里从 `messageOrder` 到 `visibleAssistantMessages`、`completedAssistantMessages`、`visibleAssistantIds`、`completedAssistantIdSet`、`visibleActivityParts`、`visibleActivitySegments`、`turnGroupingContextBase`、`renderableTurn`，是一整条 memo 链；`MessageList` 外层又有 `baseDisplayMessages`、`displayMessages`、`turns`、`renderEntries`、`stagedEntries`、索引 map 等。上游 turn 或 messages 一旦重建，下面一串都会失效。

所以这里不是“useMemo 太多”这么简单，而是“**在对象身份不稳定的前提下，用大量细粒度 useMemo 试图挽救引用稳定**”。这类写法通常会把系统推向更复杂但不更快的状态。

我的建议是：
保留真正重的 memo，比如 `baseDisplayMessages` 或 turn 投影这种明显有成本的步骤；删掉那些只是临时造 `Map/Set/小数组` 的 memo，尤其是紧贴 render 的那些。`visibleAssistantIds`、`completedAssistantIdSet`、`messageIndexMap`、`turnIndexMap`、`ProgressiveGroup` 里一部分小 memo，都很像“省不了多少，反而放大失效链”。

第 3 点，消息重用检查逻辑是否必要。

现在这套 `areMessagesEquivalentForReuse / arePartsEquivalentForReuse`，我认为 **收益不够，成本太高**。它比较了 message id、completedAt、role、finish、status、parts 长度、text/reasoning 文本、tool 状态，甚至还会去看 Pi assistant 里的 toolCall block 数量。这个检查本身已经很重，而且很脆。

更麻烦的是，它运行在 `collapseAssistantMessageChains` 之后。也就是说 assistant 链先被 merge 成 synthetic message；而 merged message 的 id 又是 `${turnId}:assistant:${firstId}:${lastId}`。只要流式过程中链尾新增/变化，merged id 就会变，之前为了“复用 summary/activity”做的大量深比较，价值会被明显削弱。

所以这块我不建议继续加规则，应该直接换思路：

把“能否复用”从深比较，改成 turn revision/signature。
例如用这些字段组成一个轻量签名：
`userMessageId + assistant sourceMessageIds + assistant stopReasons + toolCallIds + toolExecution revision`

签名没变，直接复用上次 summary/activity。
签名变了，整 turn 重算。

这样逻辑会更短，也更不容易漏边界。

第 4 点，RAF 批量更新和虚拟列表冲突。

这里冲突非常明显，而且是双层的。

第一层，`useEventStream` 用 `requestAnimationFrame` 延后把 `PiClientState` 投影进 store。第二层，`MessageList` 的 virtualizer 又是异步 forceRender，而且 `useFlushSync: false`。再往上，`scrollToTurnId / scrollToMessageId / restoreViewportAnchor` 又靠额外的 RAF 重试来等 DOM 出现。于是数据更新、React commit、虚拟列表测量、滚动修正，全都不在同一个时序里。

你现在代码里已经出现很多“症状型补丁”：

* `lastNonEmptyVirtualRowsRef`，当 virtual rows 突然空了就复用上一帧
* scroll 后再 RAF 重试找元素
* anchor restore 失败后再 RAF 重试
* 关闭 `flushSync`
* streaming 高度靠 `measureElement` 动态量

这些都说明“数据到了，但 DOM/测量还没稳”。这正是虚拟列表最怕的状态。

另外还有一个直接导致“不显示”的逻辑：`TurnBlock` 在 `sorted` 模式下只展示 completed assistant messages；如果当前 turn 还在工具调用或尚未 completion，就会只显示 completed 部分，甚至退化成只显示第一条 assistant。activity 也会按 completed assistant id 过滤。用户看到的就会是“明明流式到了，但有些内容没显示”。这不是纯渲染 bug，而是当前 sorted 模式和 streaming 混用的设计冲突。

我建议的修法不是继续调 RAF，而是：

把“历史消息”和“流式尾巴”拆开。
历史区可以虚拟化。
最新 streaming turn 单独放在虚拟列表外，常驻真实 DOM。

这样动态高度、reasoning/tool 展开、流式 token、滚动锚点，全都集中在最后一个非虚拟节点里，虚拟列表只负责稳定历史。这个收益会非常大。

第 5 点，是否应该废弃 `ChatMessageEntry`。

我的答案是：**应该退出热路径，但不要第一刀就全删。**

更准确地说，是：

* `PiSessionViewState` 继续做唯一真相源
* turn 投影直接基于 Pi raw message + toolExecutions 做
* `ChatMessageEntry` 不再作为“全会话级中间模型”
* 只在少数旧渲染组件真的需要 runtime `Part` 形状时，做局部、惰性的 adapter

现在 `ChatMessageEntry` 最大的问题不是“多一层”，而是“多一层且有业务语义”。它既影响 identity，又影响显示语义，还影响复用逻辑。热路径保留它，后面越修越难。

我建议的新结构是：

`PiSessionViewState + toolExecutions`
→ `DirectTurnProjection`
→ `HistoryTurns (cached)` + `LiveTurn (incremental)`
→ UI

其中：

* history turns 只在 finalized 后冻结
* live turn 增量更新
* 工具输出按 `toolCallId` 直接挂在 live turn 上
* 不再生成 merged synthetic assistant message id 作为主标识
* turn 内保留 `sourceMessageIds`，但 DOM 主 key 尽量稳定

具体修复建议，按执行顺序给。

第一阶段，先止血。

1. 只保留一条 tool result 显示路径。
   正常工具完成时，不要再把 `toolResult` 当普通消息 append 到消息流；或者至少把它标成 non-renderable/system，并在 `projectTurnRecords` 里排除。
   预期收益：重复显示大概率直接消失，turn 投影输入规模也会下降。

2. `sorted` 模式下不要过滤 live tail。
   历史 turn 可以 sorted；最后一个 streaming turn 强制 live 展示，不要套 completed assistant 过滤。
   预期收益：解决“内容到了但不显示”的主观体验问题。

3. 给 `PiSessionViewState` 建 `messageById` / `assistantById` / `toolExecutionByCallId` 索引。
   不要在 `MessageList` 里反复 `session.messages.find(...)`。现在 `findPiMessageById` 是线性查找，而且被多个 helper 热调用。
   预期收益：明显降低热路径查找成本，尤其长会话。

第二阶段，降成本。

4. 去掉 `useEventStream` 的全量 RAF 投影。
   至少先改成“仅更新 active session 的 store slice”；更理想的是直接把 piSessions 放进一个 store，UI 通过 selector 读当前 session，不再每帧重建多个 Map/Session 列表。
   预期收益：这是最大性能收益项，流式 token 时 CPU 占用会明显下去。

5. 拆分列表：历史虚拟化，live tail 非虚拟化。
   不要让最新 streaming turn 进入虚拟列表。
   同时删掉 `lastNonEmptyVirtualRowsRef` 这种 stale row fallback。
   预期收益：滚动锚点、重复闪烁、空窗、测量抖动都会减少。

6. 把深度复用比较改成 turn signature。
   直接删 `areMessagesEquivalentForReuse` 这套深比较，换成更短的 revision。
   预期收益：减少 CPU 消耗，也减少“明明没必要重算但被误判重算”的情况。

第三阶段，收架构。

7. 让 `projectTurnRecords` 直接吃 Pi raw 数据，不再先构造整套 `ChatMessageEntry[]`。
   `buildMinimalMessageEntryFromPi` 可以保留成兼容层，但只在局部 leaf 组件中使用。
   预期收益：层数变少、identity 更稳定、问题边界更清楚。

8. 取消 merged synthetic assistant message 作为主显示实体。
   turn 内保留原始 assistant message 列表；需要 merge 只做显示层 merge，不改主 id。
   预期收益：减少滚动定位错乱、缓存失效和 turn 全体重建。

预期收益我给保守版：

修完第 1 阶段后：

* 重复工具结果问题，大概率能直接解决
* “流式时偶尔不显示”的主观 bug 会明显减少
* 列表内容正确性会先稳定下来

修完第 2 阶段后：

* 流式阶段的 JS 计算量会明显下降
* 虚拟列表滚动/测量抖动会明显减少
* 长会话下卡顿会比现在好很多

修完第 3 阶段后：

* 才能真正把这条渲染链从“兼容式堆叠”收敛成“Pi-native 单模型”
* 后续再修样式、交互、动画，就不会一直被数据层反噬

如果只允许先做三件事，我建议按这个顺序：
先删 toolResult 双路径；再把 live tail 从虚拟列表拆出去；再去掉 `useEventStream` 的全量 RAF 投影。
这三刀最值。
